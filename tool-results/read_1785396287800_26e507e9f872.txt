    24→## 1. TestDisk
    25→
    26→### Overview
    27→TestDisk is a free and open-source data recovery utility designed primarily to recover lost partitions and repair corrupted filesystems. It is maintained by Christophe Grenier (CGSecurity) and distributed alongside PhotoRec.
    28→
    29→### What It Does
    30→- **Partition recovery**: Scans for lost/deleted partition tables and rebuilds them
    31→- **Boot sector repair**: Rebuilds corrupted boot sectors (FAT12/16/32, NTFS boot sector)
    32→- **Filesystem repair**: Fixes corrupted MFT (NTFS), FAT tables, ext2/3/4 superblocks
    33→- **File undelete**: Recovers deleted files from supported filesystems (limited capability)
    34→- **Partition table rewriting**: Can write recovered partition tables back to disk
    35→
    36→### Supported Filesystems
    37→| Filesystem | Read | Write/Repair | Notes |
    38→|---|---|---|---|
    39→| FAT12/16/32 | Yes | Yes | Boot sector repair, FAT rebuilding |
    40→| NTFS | Yes | Yes | MFT repair, boot sector rebuild |
    41→| exFAT | Yes | Limited | Partition recovery mainly |
    42→| ext2/ext3/ext4 | Yes | Yes | Superblock recovery |
    43→| HFS/HFS+ | Yes | Limited | Partition recovery |
    44→| ReiserFS | Yes | Limited | Via NTFS-3G integration |
    45→| UFS/UFS2 | Yes | Limited | BSD/Sun partition tables |
    46→| Sun Solaris | Yes | No | Partition table recovery |
    47→| BSD disklabel | Yes | No | Partition table recovery |
    48→
    49→### Architecture
    50→- **Language**: Pure C (ANSI C)
    51→- **Source structure**: Monolithic single-binary architecture; TestDisk and PhotoRec share a common codebase
    52→- **Build system**: Autoconf/Automake with `./configure && make`
    53→- **UI**: Interactive text-based (ncurses) menu-driven interface; no headless/library mode
    54→- **Disk access**: Direct device access via OS-level APIs (Linux `/dev/`, Windows `\\.\PhysicalDrive`)
    55→- **Key modules**:
    56→  - `src/` directory: `testdisk.c` (main), `partauto.c` (auto-detection), `tdiskop.c` (disk operations)
    57→  - Filesystem-specific handlers in separate files (e.g., `ntfs.c`, `fat.c`, `ext2.c`)
    58→  - Partition table handlers: `parti386.c` (MBR), `partgpt.c` (GPT), `partsun.c`, `partmac.c`
    59→
    60→### Library Usability
    61→- **NOT designed as a library**. TestDisk is a standalone CLI/interactive tool.
    62→- No exported API, no shared library (.so/.dll), no header files for programmatic use.
    63→- **Integration options**:
    64→  - Fork and extract the filesystem-specific recovery logic (significant refactoring needed)
    65→  - Shell out to the CLI and parse output (fragile, limited)
    66→  - The partition detection logic in `partauto.c` could be extracted with moderate effort
    67→
    68→### License
    69→- **GPL v2+** (GNU General Public License version 2 or later)
    70→- This means any derivative work must also be GPL v2+
    71→
    72→### Limitations
    73→- No library/API mode; tightly coupled to interactive UI
    74→- No network/remote disk support
    75→- Limited file undelete (not as robust as dedicated carving tools)
    76→- No APFS support
    77→- No Btrfs support
    78→- No ZFS support
    79→- No parallel processing/multi-threading
    80→- No progress reporting API for GUI integration
    81→- Monolithic architecture makes extracting individual components difficult

    85→## 2. PhotoRec
    86→
    87→### Overview
    88→PhotoRec is a free and open-source file carving utility that recovers deleted files by scanning raw disk data for file signatures, independent of the filesystem. It is bundled with TestDisk and shares the same codebase.
    89→
    90→### What It Does
    91→- **File carving**: Recovers files from damaged, formatted, or corrupted media regardless of filesystem state
    92→- **Read-only operation**: Never writes to the source media; always operates non-destructively
    93→- **Broad format support**: 300+ file families, 480+ file extensions
    94→- **Custom signatures**: Supports user-defined signature files for custom file types
    95→
    96→### How the Carving Engine Works
    97→PhotoRec's carving engine is **not** a simple header-footer carver. It uses a multi-layered approach:
    98→
    99→1. **Signature scanning**: Scans raw disk data block-by-block looking for known file header signatures (magic bytes)
   100→2. **File-type-specific parsing**: Once a signature is found, type-specific parsers validate and extract the file:
   101→   - **Structured formats** (JPEG, PNG, PDF, DOCX): Parse internal structure to determine file size
   102→   - **Container formats** (ZIP, RAR, 7z): Parse headers to find end-of-archive markers
   103→   - **Video formats** (MP4, AVI, MOV): Parse atom/chunk structure for boundaries
   104→   - **RAW camera formats** (CR2, NEF, ORF): Parse TIFF/EXIF-like structures
   105→3. **Fragment handling**: For some formats, PhotoRec can handle fragmented files by looking for continuation markers
   106→4. **Validation**: Recovered files are validated against known format constraints
   107→5. **Custom signatures**: Users can define custom signatures via a `photorec.sig` file with header bytes, offset, and file extension
   108→
   109→### Supported File Formats (Major Categories)
   110→| Category | Examples | Count |
   111→|---|---|---|
   112→| Images | JPEG, PNG, GIF, TIFF, BMP, RAW (CR2, NEF, ORF, DNG, ARW) | 80+ |
   113→| Video | MP4, AVI, MOV, MKV, WMV, FLV, 3GP | 30+ |
   114→| Audio | MP3, WAV, OGG, FLAC, AAC, WMA | 20+ |
   115→| Documents | PDF, DOC/DOCX, XLS/XLSX, PPT/PPTX, ODT, RTF | 40+ |
   116→| Archives | ZIP, RAR, 7z, TAR, GZ, BZ2 | 20+ |
   117→| Database | MDB, SQL, DBF, SQLite | 10+ |
   118→| Executable | EXE, DLL, ELF | 5+ |
   119→| Other | ISO, VMDK, VHD, eml, mbox | 50+ |
   120→
   121→### Architecture
   122→- **Language**: Pure C (ANSI C), same codebase as TestDisk
   123→- **Source structure**: File-type-specific parsers in `src/` directory (e.g., `file_jpg.c`, `file_pdf.c`, `file_mp4.c`)
   124→- **Carving engine**: Core logic in `photorec.c` and `phrecn.c`
   125→- **Signature database**: Compiled into the binary from individual `file_*.c` files
   126→- **Session management**: Supports resume/continue interrupted recovery sessions
   127→- **Output**: Files recovered to a specified output directory with sequential naming
   128→
   129→### Library Usability
   130→- **NOT designed as a library**. Like TestDisk, it is a standalone CLI/interactive tool.
   131→- No exported API, no shared library, no header files.
   132→- **Integration options**:
   133→  - The file-type-specific parsers (e.g., `file_jpg.c`, `file_mp4.c`) are relatively self-contained and could be extracted
   134→  - The carving engine core (`photorec.c`) is tightly coupled to the interactive UI
   135→  - CLI invocation with output parsing is the simplest integration path
   136→  - Autopsy (by TSK) integrates PhotoRec as a module by invoking it as a subprocess
   137→
   138→### License
   139→- **GPL v2+** (same as TestDisk)
   140→
   141→### Limitations
   142→- No library/API mode; interactive UI only
   143→- File names are lost (carved files get sequential names like `f0000001.jpg`)
   144→- No directory structure recovery (inherent to carving)
   145→- No support for fragmented files in most formats
   146→- Single-threaded processing
   147→- No network/remote source support
   148→- No progress callback API
   149→- No built-in deduplication of recovered files
   150→- Cannot recover files smaller than the filesystem block size

   154→## 3. The Sleuth Kit (TSK) / libtsk
   155→
   156→### Overview
   157→The Sleuth Kit (TSK) is a collection of command-line tools and a **C library (libtsk)** for analyzing disk images and recovering files. It is the most mature and library-friendly open-source forensic tool available. TSK powers Autopsy (its GUI front-end) and many other commercial and open-source tools.
   158→
   159→### Supported Filesystems
   160→| Filesystem | Read | Write | Notes |
   161→|---|---|---|---|
   162→| NTFS | Yes | No | Full MFT parsing, ADS support |
   163→| FAT12/16/32 | Yes | No | Full directory parsing |
   164→| exFAT | Yes | No | |
   165→| ext2/ext3/ext4 | Yes | No | Full inode parsing |
   166→| HFS/HFS+ | Yes | No | |
   167→| HFSX | Yes | No | |
   168→| UFS1/UFS2 | Yes | No | |
   169→| YAFFS2 | Yes | No | Embedded/Android |
   170→| ISO 9660 | Yes | No | CD-ROM |
   171→| APFS | Partial | No | Limited/experimental support |
   172→| LVM | Yes | No | Volume management layer |
   173→
   174→### Volume System Support
   175→| Type | Support |
   176→|---|---|
   177→| MBR/DOS | Yes |
   178→| GPT | Yes |
   179→| BSD Disklabel | Yes |
   180→| Sun VTOC | Yes |
   181→| Mac Partition Map | Yes |
   182→| LVM | Yes |
   183→| RAID (mdadm) | Limited |
   184→| LUKS | No (encrypted) |
   185→
   186→### Library API (libtsk)
   187→TSK is **designed as a library** with a well-documented C API. Key API groups:
   188→
   189→#### Image Layer
   190→```c
   191→TSK_IMG_INFO *tsk_img_open_utf8_sing(const char *a_utf8, TSK_IMG_TYPE_ENUM a_type, unsigned int a_ssize);
   192→TSK_IMG_INFO *tsk_img_open_sing(const char *a_image, TSK_IMG_TYPE_ENUM a_type, unsigned int a_ssize);
   193→uint8_t tsk_img_read(TSK_IMG_INFO *a_img_info, TSK_OFF_T a_offset, char *a_buf, size_t a_len);
   194→void tsk_img_close(TSK_IMG_INFO *a_img_info);
   195→```
   196→
   197→#### Volume System Layer
   198→```c
   199→TSK_VS_INFO *tsk_vs_open(TSK_IMG_INFO *a_img_info, TSK_DADDR_T a_offset, TSK_VS_TYPE_ENUM a_type);
   200→TSK_VS_PART_INFO *tsk_vs_part_get(TSK_VS_INFO *a_vs_info, int a_index);
   201→void tsk_vs_close(TSK_VS_INFO *a_vs_info);
   202→```
   203→
   204→#### Filesystem Layer
   205→```c
   206→TSK_FS_INFO *tsk_fs_open_img(TSK_IMG_INFO *a_img_info, TSK_OFF_T a_offset, TSK_FS_TYPE_ENUM a_type);
   207→TSK_FS_FILE *tsk_fs_file_open_meta(TSK_FS_INFO *a_fs, TSK_FS_FILE *a_fs_file, TSK_INUM_T a_addr);
   208→TSK_FS_FILE *tsk_fs_file_open(TSK_FS_INFO *a_fs, TSK_FS_FILE *a_fs_file, const char *a_path);
   209→ssize_t tsk_fs_file_read(TSK_FS_FILE *a_fs_file, TSK_OFF_T a_offset, char *a_buf, size_t a_len, TSK_FS_FILE_READ_FLAG_ENUM a_flags);
   210→uint8_t tsk_fs_dir_walk(TSK_FS_INFO *a_fs, TSK_INUM_T a_addr, TSK_FS_DIR_WALK_FLAG_ENUM a_flags, TSK_FS_DIR_WALK_CB a_action, void *a_ptr);
   211→uint8_t tsk_fs_fls(TSK_FS_INFO *a_fs, TSK_TCHAR **a_argv);
   212→void tsk_fs_close(TSK_FS_INFO *a_fs);
   213→```
   214→
   215→#### Key Features of the API
   216→- **Layered architecture**: Image → Volume System → Filesystem → File (clean abstraction)
   217→- **Callback-based iteration**: `tsk_fs_dir_walk()`, `tsk_fs_file_walk()` for directory traversal
   218→- **Autodetection**: `tsk_fs_open_img()` can auto-detect filesystem type with `TSK_FS_TYPE_DETECT`
   219→- **Java bindings**: Official JNI bindings available (`bindings/java/`)
   220→- **Python bindings**: Available via third-party `pytsk` wrapper
   221→
   222→### Language Bindings
   223→| Language | Binding | Status |
   224→|---|---|---|
   225→| C | libtsk (native) | Official, full API |
   226→| Java | JNI bindings | Official, in repo |
   227→| Python | pytsk | Third-party, partial |
   228→| C++ | Direct C linkage | Trivial |
   229→| .NET | TSK wrapper | Third-party, limited |
   230→
   231→### Limitations for Recovery (vs. Forensics)
   232→- **Read-only**: TSK is designed for forensic analysis, not repair. It cannot write/repair filesystems.
   233→- **No partition recovery**: Cannot rebuild partition tables (unlike TestDisk)
   234→- **No file carving**: TSK does not include a carving engine (relies on filesystem metadata)
   235→- **No deleted file recovery guarantee**: Deleted files may have overwritten metadata; TSK can find them but cannot guarantee content
   236→- **No APFS full support**: APFS is still experimental/incomplete
   237→- **No Btrfs/ZFS support**: Missing modern Linux filesystems
   238→- **No encrypted volume support**: Cannot handle BitLocker, LUKS, FileVault
   239→- **Single-threaded**: Core operations are not multi-threaded
   240→- **No disk imaging**: Cannot create disk images (unlike ddrescue)
   241→
   242→### License
   243→- **Mixed licensing** (important for commercial use):
   244→  - **Core library (libtsk)**: Predominantly **IBM Public License v1.0** and **Common Public License v1.0 (CPL)**
   245→  - **Some tools**: **GPL v2+**
   246→  - **Some modules**: **LGPL**
   247→  - The IBM CPL and CPL are **OSI-approved** and generally compatible with commercial use (similar to LGPL in effect)
   248→  - **Critical**: The library portion can be linked into commercial applications without requiring the application to be open-sourced, but the specific license terms must be carefully reviewed per-module
   249→
   250→### Integration Verdict
   251→- **Best candidate for library integration** among all tools researched
   252→- Well-documented C API with stable ABI
   253→- Existing commercial products use libtsk (e.g., some forensic tools)
   254→- Java bindings available for JVM-based projects
   255→- The read-only nature is actually a feature for recovery (non-destructive analysis)

   259→## 4. Untrunc
   260→
   261→### Overview
   262→Untrunc is a specialized open-source tool for repairing corrupted/truncated MP4, MOV, M4V, and 3GP video files. It is particularly useful for recovering video from dashcams, bodycams, smartphones, and drones where recording was interrupted.
   263→
   264→### What It Does
   265→- Repairs MP4/MOV files with missing or corrupted `moov` atom (metadata block)
   266→- Recovers truncated video files where recording was interrupted
   267→- Reconstructs the `moov` atom using a healthy reference video from the same device
   268→- Handles H.264, H.265, and other codec streams within MP4 containers
   269→
   270→### How It Works
   271→The repair process operates in **three phases**:
   272→
   273→1. **Reference Analysis**: Untrunc reads the `moov` atom from the healthy reference video, extracting:
   274→   - Codec parameters (H.264 profile, level, SPS/PPS)
   275→   - Sample table structure (sample sizes, offsets, durations)
   276→   - Track layout and timing information
   277→   - Audio/video synchronization metadata
   278→
   279→2. **Stream Parsing**: Untrunc scans the broken file byte-by-byte, identifying:
   280→   - `mdat` atom boundaries (raw media data)
   281→   - Individual NAL units (Network Abstraction Layer units for H.264)
   282→   - Audio frames (AAC, PCM, etc.)
   283→   - Sync points (keyframes/I-frames)
   284→
   285→3. **Reconstruction**: A new `moov` atom is constructed by:
   286→   - Mapping the identified media data to sample table entries
   287→   - Calculating offsets, sizes, and durations for each sample
   288→   - Building the track structure based on the reference template
   289→   - Writing the repaired file with a valid `moov` atom prepended/appended
   290→
   291→### Architecture
   292→- **Language**: C++ (original by Federico Dossena), with active forks in C++
   293→- **Source**: Single-file architecture (`untrunc.cpp`), relatively simple
   294→- **Dependencies**: FFmpeg (libavcodec, libavformat) for codec parsing
   295→- **Build**: Simple Makefile or CMake
   296→- **Active fork**: `anthwlock/untrunc` on GitHub (10x faster, lower memory, fixes)
   297→
   298→### Library Usability
   299→- **NOT designed as a library**. Standalone CLI tool.
   300→- The core logic is in a single C++ file and could be refactored into a library with moderate effort
   301→- The reference-analysis and stream-parsing logic are separable
   302→- **Integration options**:
   303→  - Fork and wrap the core logic into a C++ library class
   304→  - CLI invocation with output parsing
   305→  - The `anthwlock` fork has cleaner code structure
   306→
   307→### License
   308→- **GPL v2.0** (original and most forks)
   309→- Some forks may have different licenses; check specific fork
   310→
   311→### Limitations
   312→- Requires a reference video from the same device/recorder (same codec settings)
   313→- Only handles MP4/MOV/3GP container formats
   314→- Cannot repair files where the `mdat` data itself is corrupted
   315→- No support for AVI, MKV, or other containers
   316→- No GUI in the original (some forks add GUIs)
   317→- No batch processing
   318→- Single-threaded
   319→- Memory-intensive for large files (original); improved in `anthwlock` fork
   320→
   321→### Integration Potential
   322→- **High value** for a recovery engine focused on video recovery
   323→- The MP4 reconstruction logic is unique and valuable
   324→- Would need refactoring from CLI to library
   325→- The FFmpeg dependency is a consideration (LGPL v2.1+ or GPL depending on build options)

   329→## 5. GNU ddrescue
   330→
   331→### Overview
   332→GNU ddrescue is a data recovery tool that copies data from one file or block device to another, with a sophisticated algorithm designed to rescue as much data as possible from failing drives while minimizing additional damage.
   333→
   334→### What Makes It Better Than dd for Failing Disks
   335→| Feature | dd | ddrescue |
   336→|---|---|---|
   337→| Error handling | Stops on first error | Skips errors, retries later |
   338→| Block size | Fixed | Adaptive (shrinks on error) |
   339→| Resume | No | Yes (mapfile-based) |
   340→| Read strategy | Sequential only | Adaptive multi-pass |
   341→| Bad sector tracking | No | Yes (mapfile) |
   342→| Trim/scrape | No | Yes (per-sector recovery) |
   343→| Progress tracking | Minimal | Detailed (mapfile) |
   344→| Additional damage risk | High (repeated reads) | Minimized (smart retry) |
   345→
   346→### Adaptive Reading Algorithm (5 Phases)
   347→
   348→#### Phase 1: Copying
   349→- Reads non-tried areas in **large blocks** (default: 128 KiB)
   350→- When a read error occurs, marks the failed block as "non-tried" at a smaller size
   351→- Skips over bad areas quickly to rescue good data first
   352→- **Key insight**: Get one good read from every accessible sector before spending time on bad ones
   353→
   354→#### Phase 2: Trimming
   355→- Reads forwards one sector at a time from the edges of bad areas
   356→- "Trims" the boundaries of unreadable regions to their minimum size
   357→- Each sector is tried at most once in this phase
   358→- **Purpose**: Recover data from the edges of bad blocks where only part of the block is damaged
   359→
   360→#### Phase 3: Sweeping (ddrescue 1.22+)
   361→- Reads the remaining non-tried blocks in reverse direction
   362→- Helps identify boundaries that might be different when reading from the opposite direction
   363→- **Purpose**: Some drives read differently depending on direction
   364→
   365→#### Phase 4: Scraping
   366→- Reads each non-scraped block forwards, **one sector at a time**
   367→- Single-sector reads are more likely to succeed than multi-sector reads
   368→- Each sector is tried at most once in this phase
   369→- **Purpose**: Recover individual sectors that failed in larger block reads
   370→
   371→#### Phase 5: Retrying (disabled by default)
   372→- Re-attempts all failed sectors with a specified number of retries
   373→- Can be configured with `--retry-passes=N`
   374→- **Purpose**: Last-resort attempt for remaining bad sectors
   375→
   376→### Mapfile
   377→- Binary mapfile tracks the status of every sector:
   378→  - `+` (rescued): Successfully read
   379→  - `-` (bad): Failed to read
   380→  - `/` (non-tried): Not yet attempted
   381→  - `?` (non-trimmed): Edge of bad area, needs trimming
   382→  - `*` (non-scraped): Needs scraping
   383→- Enables resume after interruption
   384→- Can be manually edited for advanced control
   385→
   386→### Architecture
   387→- **Language**: C++
   388→- **Source**: Single-file architecture (`ddrescue.cc`), well-structured
   389→- **I/O model**: Asynchronous I/O with non-blocking reads
   390→- **Build**: Standard GNU autotools
   391→- **No external dependencies**
   392→
   393→### Library Usability
   394→- **NOT designed as a library**. Standalone CLI tool.
   395→- The algorithm logic is in a single C++ file
   396→- **Integration options**:
   397→  - Fork and extract the core algorithm (the `Rescuebook` class)
   398→  - CLI invocation with mapfile parsing
   399→  - The algorithm is well-documented and could be reimplemented in a clean-room manner
   400→
   401→### License
   402→- **GPL v2+** (part of GNU project)
   403→- Cannot be linked into proprietary software
   404→
   405→### Limitations
   406→- No library mode
   407→- No GUI (third-party GUIs exist: ddrescueview, DDRescue-GUI)
   408→- Reads through Linux kernel block device layer (cannot send raw ATA commands)
   409→- No head-awareness (doesn't know which physical head is failing)
   410→- No SMART integration
   411→- No automatic disk health assessment
   412→- Single-threaded I/O (one read at a time)
   413→- No network/remote source support

   417→## 6. HDDSuperClone / OpenSuperClone
   418→
   419→### Overview
   420→HDDSuperClone (by Scott Dwyer) and its open-source fork OpenSuperClone (by ISpillMyDrink) are advanced Linux-based disk cloning/imaging tools specifically designed for data recovery from failing drives. They represent a significant step beyond ddrescue in their approach to failing disk handling.
   421→
   422→### What Makes It Different from ddrescue
   423→| Feature | ddrescue | HDDSuperClone/OpenSuperClone |
   424→|---|---|---|
   425→| I/O path | Linux kernel block layer | Raw ATA/SCSI commands |
   426→| Head awareness | No | Yes (head mapping) |
   427→| Read strategy | Adaptive multi-pass | Adaptive + head-skipping |
   428→| Virtual driver | No | Yes (virtual driver for OS access) |
   429→| Firmware access | No | Yes (ATA/SCSI passthrough) |
   430→| Write-blocking | No | Yes (read-only virtual driver) |
   431→| Phase management | 5 fixed phases | Configurable multi-phase |
   432→| Drive-specific tuning | No | Yes (adjustable timeouts, block sizes) |
   433→
   434→### Adaptive Reading Strategy
   435→OpenSuperClone's approach is fundamentally different from ddrescue:
   436→
   437→1. **Head-Skipping Algorithm**: 
   438→   - Deduces head boundaries from LBA error clustering
   439→   - When one head is failing, skips the entire head's LBA range
   440→   - Returns to skipped heads later (some heads may recover after rest)
   441→   - This is the key advantage: Linux software cannot read firmware geometry directly, so OSC infers it from error patterns
   442→
   443→2. **Configurable Read Modes**:
   444→   - **Standard read**: Normal kernel-level reads
   445→   - **ATA pass-through**: Sends raw ATA read commands (READ DMA, READ NATIVE MAX ADDRESS)
   446→   - **SCSI pass-through**: Raw SCSI commands for SCSI/SAS drives
   447→   - **Virtual driver**: Presents a virtual block device to the OS that proxies reads
   448→
   449→3. **Adaptive Block Sizing**:
   450→   - Starts with large block sizes for healthy areas
   451→   - Automatically reduces block size on errors
   452→   - Can be configured per-head or per-zone
   453→
   454→4. **Multi-Phase Recovery**:
   455→   - Phase 1: Quick pass (large blocks, skip errors)
   456→   - Phase 2: Head analysis (identify failing heads)
   457→   - Phase 3: Per-head recovery (skip bad heads, recover good ones)
   458→   - Phase 4: Retry bad areas with smaller blocks
   459→   - Phase 5: Final scrape (sector-by-sector)
   460→
   461→5. **Virtual Driver**:
   462→   - Creates a virtual block device (`/dev/osc0`)
   463→   - Allows the OS to mount the image while cloning is in progress
   464→   - Reads from the clone image for already-rescued sectors
   465→   - Reads from the source drive for not-yet-rescued sectors
   466→   - This enables running filesystem recovery tools on the drive while it's still being cloned
   467→
   468→### Architecture
   469→- **Language**: C (core), Python (GUI/HDDSuperClone)
   470→- **Source**: OpenSuperClone on GitHub (`ISpillMyDrink/OpenSuperClone`)
   471→- **Components**:
   472→  - `oscsuper`: Main cloning engine (C)
   473→  - `oscvt`: Virtual driver (C kernel module)
   474→  - `oscviewer`: Progress log viewer
   475→  - GUI: Python/Qt-based
   476→- **Build**: Makefile-based, requires kernel headers for virtual driver
   477→- **Live ISO**: Available for boot-and-recover scenarios
   478→
   479→### Library Usability
   480→- **NOT designed as a library**. Standalone application with GUI.
   481→- The core cloning engine is a standalone C program
   482→- **Integration options**:
   483→  - Fork and extract the head-mapping algorithm
   484→  - CLI invocation with output parsing
   485→  - The virtual driver is a kernel module that could be used independently
   486→  - The ATA/SCSI command layer is a valuable reusable component
   487→
   488→### License
   489→- **OpenSuperClone**: **GPL v2** (as stated on GitHub)
   490→- **HDDSuperClone**: Originally proprietary (closed-source), then dual-licensed; the original HDDSuperClone has a commercial license option
   491→- **Note**: HDDSuperClone's website still sells a "pro" version with additional features
   492→
   493→### Limitations
   494→- Linux-only (requires raw device access and kernel module)
   495→- No library mode
   496→- Requires root/sudo for raw device access
   497→- The virtual driver requires kernel module compilation
   498→- No Windows/macOS support
   499→- GUI is Python/Qt-based (heavy dependency)
   500→- No network/remote source support
   501→- Documentation is limited (community-driven)
   502→- The head-skipping algorithm is heuristic-based (may not work for all drives)

   616→### GPL Implications for Commercial Integration
   617→
   618→#### GPLv2
   619→- **Cannot** be linked into proprietary software (static or dynamic)
   620→- **Cannot** be used as a library in a commercial product without open-sourcing the entire product
   621→- **Can** be used as a separate process (CLI invocation) via pipe/socket if the communication is at arm's length
   622→- **Can** be distributed alongside commercial software if they are separate programs
   623→- **Derivative works** must be GPL v2
   624→
   625→#### GPLv3
   626→- Same as GPLv2 but with additional anti-tivoization and patent provisions
   627→- Stricter about "conveying" and "user product" definitions
   628→- Explicit about dynamic linking creating a derivative work
   629→
   630→#### LGPL v3
   631→- **Can** be linked (dynamically) into proprietary software
   632→- The proprietary software must allow the user to relink with a modified version of the LGPL library
   633→- Static linking is allowed if the object files are provided for relinking
   634→- **No** obligation to open-source the proprietary application
   635→- Modifications to the LGPL library itself must be shared under LGPL
   636→
   637→#### IBM CPL / CPL v1.0 (TSK)
   638→- **OSI-approved** and generally compatible with commercial use
   639→- Similar effect to LGPL: the library can be used in commercial products
   640→- Requires that the library's source code (including modifications) be made available
   641→- The application using the library is not required to be open-sourced
   642→
   643→#### Apache 2.0
   644→- **Commercial-friendly**: can be used, modified, and distributed in proprietary software
   645→- Includes patent grant from contributors
   646→- Requires attribution and license notice
   647→- Modifications must be noted but not necessarily open-sourced
   648→
   649→#### Public Domain
   650→- **No restrictions**: can be used, modified, and distributed without any obligations
   651→- No attribution required (but appreciated)
   652→- No warranty or liability
   653→
   654→### Strategies for Using GPL Code in a Commercial Product
   655→
   656→1. **Process isolation**: Run GPL tools as separate processes, communicate via pipes/sockets
   657→   - Legal gray area; the FSF considers this a "technical subterfuge" if the communication is intimate
   658→   - More defensible if the GPL tool is a standard system utility
   659→   - Example: Invoking `ddrescue` as a subprocess and parsing its mapfile
   660→
   661→2. **Plugin architecture**: Design the core engine to load GPL code as optional plugins
   662→   - Users must install GPL plugins separately
   663→   - The core engine must be useful without the GPL plugins
   664→   - This is the approach used by some commercial forensic tools
   665→
   666→3. **Clean-room reimplementation**: Study the GPL code's behavior, then reimplement from scratch
   667→   - Must be done by a developer who has not read the GPL source code
   668→   - A separate "dirty room" team studies the code and writes specifications
   669→   - A "clean room" team implements from specifications only
   670→   - This is the most legally defensible approach but also the most expensive
   671→
   672→4. **Dual licensing**: Contact the copyright holder for a commercial license
   673→   - Some projects (e.g., HDDSuperClone) offer this
   674→   - May be expensive or unavailable
   675→
   676→5. **Use permissively-licensed alternatives**:
   677→   - **Scalpel (Apache 2.0)** instead of PhotoRec for carving
   678→   - **libyal (LGPL)** instead of TSK for filesystem parsing
   679→   - **Foremost (Public Domain)** for basic carving
   680→   - **libtsk (IBM CPL)** for filesystem analysis

   827→## 10. Summary & Recommendations
   828→
   829→### Key Findings
   830→
   831→1. **The Sleuth Kit (libtsk) is the best foundation** for a data recovery engine. It is the only tool with a proper C library API, permissive licensing (IBM CPL/CPL), and comprehensive filesystem support. It should be the core of any recovery engine.
   832→
   833→2. **libyal libraries are the best complement** for filesystem parsing. They are LGPL-licensed, library-first, and cover NTFS, VMDK, VHDX, and other formats not fully supported by TSK.
   834→
   835→3. **Scalpel (Apache 2.0) is the best carving engine** for commercial integration. It is fast, configurable, and permissively licensed. It lacks PhotoRec's format breadth but is extensible.
   836→
   837→4. **GPL tools (TestDisk, PhotoRec, ddrescue, Untrunc, OpenSuperClone) cannot be directly linked** into a commercial product. They can be used as subprocesses or as references for clean-room reimplementation.
   838→
   839→5. **The most valuable GPL algorithms to reimplement** are:
   840→   - ddrescue's adaptive reading algorithm (well-documented, medium complexity)
   841→   - Untrunc's MP4 moov reconstruction (well-understood, medium complexity)
   842→   - TestDisk's partition detection (well-documented, medium complexity)
   843→
   844→6. **The PhotoRec signature database** (480+ file formats) is extremely valuable but trapped in GPL code. A clean-room reimplementation of the signature database (as a data file, not code) may be feasible.
   845→
   846→7. **OpenSuperClone's head-skipping algorithm** is the most valuable advanced feature but also the most complex to reimplement. It requires deep ATA/SCSI knowledge.
   847→
   848→### Recommended Integration Roadmap
   849→
   850→| Phase | Components | Timeline | License |
   851→|---|---|---|---|
   852→| **Phase 1: Core** | libtsk + libyal + Scalpel | 2-3 months | IBM CPL / LGPL / Apache 2.0 |
   853→| **Phase 2: Imaging** | Clean-room ddrescue-like algorithm | 2-3 months | Proprietary |
   854→| **Phase 3: Partition** | Clean-room partition recovery | 2-3 months | Proprietary |
   855→| **Phase 4: Carving** | Extended Scalpel + custom signatures | 2-3 months | Apache 2.0 + proprietary |
   856→| **Phase 5: Video** | Clean-room MP4 repair | 1-2 months | Proprietary |
   857→| **Phase 6: Advanced** | GPL subprocess integration (ddrescue, PhotoRec, OSC) | 2-3 months | GPL (optional) |
   858→| **Phase 7: Head-aware** | Clean-room head-skipping algorithm | 3-6 months | Proprietary |
