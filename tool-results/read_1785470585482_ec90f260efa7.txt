    15→## 1. Internal Architecture of Data Recovery Software
    16→
    17→### 1.1 Core Modules
    18→
    19→Professional data recovery tools (R-Studio, DMDE, UFS Explorer, DiskDrill) share a common architectural pattern composed of several layered modules:
    20→
    21→```
    22→┌─────────────────────────────────────────────────────┐
    23→│                   UI / Presentation Layer            │
    24→│  (File tree, hex viewer, scan progress, recovery)   │
    25→├─────────────────────────────────────────────────────┤
    26→│              Filesystem Reconstruction Engine        │
    27→│  (Virtual FS builder, directory tree, metadata)     │
    28→├────────────┬────────────┬────────────┬──────────────┤
    29→│  NTFS      │  APFS      │  EXT4      │  FAT/exFAT   │
    30→│  Parser    │  Parser    │  Parser    │  Parser      │
    31→├────────────┴────────────┴────────────┴──────────────┤
    32→│              File Carving / Signature Scanner        │
    33→│  (Magic number detection, structure parsing,        │
    34→│   fragmented reassembly)                            │
    35→├─────────────────────────────────────────────────────┤
    36→│              RAID / Volume Assembly Layer            │
    37→│  (Virtual RAID, stripe detection, parity calc)      │
    38→├─────────────────────────────────────────────────────┤
    39→│              Partition / Volume Detection            │
    40→│  (MBR, GPT, APM, BSD label, LVM, dynamic disks)    │
    41→├─────────────────────────────────────────────────────┤
    42→│              Raw Disk I/O Layer                      │
    43→│  (ATA/SCSI commands, device access, error handling) │
    44→└─────────────────────────────────────────────────────┘
    45→```
    46→
    47→### 1.2 Internal Flow: Raw Disk Read → File Recovery
    48→
    49→The typical recovery pipeline proceeds as follows:
    50→
    51→1. **Device Discovery & Enumeration**: The I/O layer enumerates available storage devices using OS APIs (Windows: `CreateFile` with `\\.\PhysicalDriveN`; Linux: `/dev/sdX`; macOS: `/dev/diskN`). USB drives attached via USB-bridge controllers are handled differently from direct SATA/PCIe devices.
    52→
    53→2. **Disk Imaging (Optional but Recommended)**: Before any logical analysis, a sector-by-sector image is created. Professional tools use adaptive reading strategies (see §8).
    54→
    55→3. **Partition Table Scan**: The tool scans for partition structures — MBR (at LBA 0), GPT (LBA 1 for header, LBA 2-33 for entries), APM, BSD disklabels, LVM2 PV headers, Windows dynamic disk LDM databases. If partition tables are corrupted, the tool performs a **surface scan** looking for filesystem signatures at sector boundaries.
    56→
    57→4. **Filesystem Detection**: For each partition/volume found, the tool identifies the filesystem type by examining the boot sector / superblock / NX superblock. If the volume header is missing, the tool may attempt to detect the filesystem type by scanning for characteristic on-disk structures (e.g., MFT signatures "FILE" for NTFS, superblock magic 0xEF53 for EXT4).
    58→
    59→5. **Filesystem Parsing**: The filesystem-specific parser reads metadata structures (MFT, catalog file, inode table, FAT, etc.) and builds an in-memory representation of the directory tree and file metadata.
    60→
    61→6. **Deleted File Detection**: The parser checks for files marked as deleted in the filesystem metadata. For NTFS, this means MFT entries with the "in-use" flag cleared. For EXT4, it means inodes with a link count of 0 and deleted directory entries. For FAT, it means directory entries with 0xE5 as the first byte.
    62→
    63→7. **Filesystem Reconstruction**: For damaged filesystems, the tool attempts to reconstruct the directory tree using heuristics, journal data, and secondary metadata sources (see §7).
    64→
    65→8. **File Carving (Fallback)**: If filesystem metadata is completely unavailable, the tool falls back to signature-based carving to recover files by content (see §6).
    66→
    67→9. **File Assembly & Recovery**: For each file to be recovered, the tool resolves the cluster/extent chain, reads the data blocks, and writes them to the output destination. For fragmented files, the tool must correctly reassemble the fragments.
    68→
    69→### 1.3 Tool-Specific Notes
    70→
    71→- **R-Studio**: Known for its very fast scan speed and strong filesystem reconstruction. Supports a wide range of filesystems. Has advanced RAID reconstruction with automatic parameter detection. Uses a multi-pass scan approach: first a quick scan for existing metadata, then a deep scan for carving.
    72→
    73→- **DMDE**: Lightweight but extremely powerful. Known for its virtual filesystem reconstruction that can handle severely damaged filesystems. Uses a unique "FS fragments" approach where it identifies fragments of filesystem metadata scattered across the disk and merges them. Its INDX processing for NTFS is particularly sophisticated — it can reconstruct directory structure from INDX attributes even when MFT entries are damaged.
    74→
    75→- **UFS Explorer**: Known for its support of exotic filesystems and RAID configurations. Has specialized recovery algorithms for different storage types (NAS, RAID, etc.). Uses a "storage reconstruction" approach.
    76→
    77→- **DiskDrill**: More consumer-oriented but uses similar underlying technology. Focuses on ease of use with its "Recovery Vault" (which pre-records metadata for future recovery) and "Guaranteed Recovery" features.

    81→## 2. NTFS Parser Design
    82→
    83→### 2.1 Core NTFS On-Disk Structures
    84→
    85→NTFS (New Technology File System) is the primary filesystem for Windows. Its core concept is: **everything is (or is stored in) a file.** There is no separate metadata plane like inodes in UNIX — instead, the Master File Table (MFT) serves as the central metadata structure.
    86→
    87→#### 2.1.1 The Boot Sector ($Boot)
    88→
    89→Located at the first sector of the volume. Contains:
    90→- OEM ID ("NTFS    ")
    91→- Bytes per sector (typically 512 or 4096)
    92→- Sectors per cluster (power of 2)
    93→- MFT cluster number (byte offset to the start of $MFT)
    94→- MFT mirror cluster number
    95→- Size of MFT entries (typically 1024 bytes, stored as a signed exponent: -10 means 2^10 = 1024)
    96→- Clusters per index record (typically 4096 bytes)
    97→
    98→#### 2.1.2 The Master File Table ($MFT)
    99→
   100→The MFT is a sequence of 1024-byte entries (by default). Each entry describes one file or directory. The first 16-24 entries are reserved for system files:
   101→
   102→| Entry | File | Purpose |
   103→|-------|------|---------|
   104→| 0 | $MFT | The MFT itself (self-referencing) |
   105→| 1 | $MFTMirr | Mirror copy of first 4 MFT entries |
   106→| 2 | $LogFile | Journal for transaction safety |
   107→| 3 | $Volume | Volume information (label, flags, serial) |
   108→| 4 | $AttrDef | Attribute definitions |
   109→| 5 | . (root) | Root directory |
   110→| 6 | $Bitmap | Cluster allocation bitmap |
   111→| 7 | $Boot | Boot sector |
   112→| 8 | $BadClus | Bad cluster list |
   113→| 9 | $Secure | Security descriptors |
   114→| 10 | $UpCase | Uppercase character table |
   115→| 11 | $Extend | Extended metadata directory |
   116→| 12-15 | Reserved | Reserved for future use |
   117→| 16-23 | System | Additional system files |
   118→
   119→#### 2.1.3 MFT Entry Structure
   120→
   121→Each MFT entry has this structure:
   122→
   123→```
   124→┌────────────────────────────────┐
   125→│ MFT Entry Header (42+ bytes)   │
   126→│  - Signature: "FILE" or "BAAD" │
   127→│  - Fixup offset & count        │
   128→│  - Sequence number             │
   129→│  - Hard link count             │
   130→│  - Offset to first attribute   │
   131→│  - Flags (in-use, directory)   │
   132→│  - Used size / Allocated size  │
   133→├────────────────────────────────┤
   134→│ Fixup Array                    │
   135→│  (2-byte signature + original  │
   136→│   last-2-bytes of each sector) │
   137→├────────────────────────────────┤
   138→│ Attribute 1 (header + content) │
   139→├────────────────────────────────┤
   140→│ Attribute 2 (header + content) │
   141→├────────────────────────────────┤
   142→│ ...                            │
   143→├────────────────────────────────┤
   144→│ 0xFFFFFFFF (end marker)        │
   145→├────────────────────────────────┤
   146→│ Unused space                   │
   147→└────────────────────────────────┘
   148→```
   149→
   150→**Fixup Arrays**: NTFS uses fixup arrays as a form of integrity checking. For each sector in the MFT entry, the last 2 bytes are replaced with a 2-byte signature. The original values are stored in the fixup array. When parsing, you must first undo the fixup to get the correct data. If the signature doesn't match at the end of a sector, the sector is likely corrupted.
   151→
   152→#### 2.1.4 Attribute Types
   153→
   154→Each MFT entry contains a sequence of attributes. Common attribute types:
   155→
   156→| Type ID | Name | Description |
   157→|---------|------|-------------|
   158→| 0x10 | $STANDARD_INFORMATION | File timestamps, permissions, attributes |
   159→| 0x20 | $ATTRIBUTE_LIST | For files needing multiple MFT entries |
   160→| 0x30 | $FILE_NAME | File name, parent directory ref, timestamps, sizes |
   161→| 0x40 | $OBJECT_ID | Unique object identifier |
   162→| 0x50 | $SECURITY_DESCRIPTOR | Security/ACL data |
   163→| 0x60 | $VOLUME_NAME | Volume name |
   164→| 0x70 | $VOLUME_INFORMATION | Volume version and flags |
   165→| 0x80 | $DATA | File data content |
   166→| 0x90 | $INDEX_ROOT | Directory index root |
   167→| 0xA0 | $INDEX_ALLOCATION | Directory index blocks (INDX) |
   168→| 0xB0 | $BITMAP | Allocation bitmap for index |
   169→| 0xC0 | $REPARSE_POINT | Symbolic link / mount point target |
   170→| 0x100 | $LOGGED_UTILITY_STREAM | EFS encrypted data |
   171→
   172→#### 2.1.5 Resident vs. Non-Resident Attributes
   173→
   174→- **Resident attributes**: The attribute content is stored directly within the MFT entry. Small files (typically under ~700 bytes) can have their entire $DATA attribute stored as resident, meaning the file content is inside the MFT entry itself.
   175→
   176→- **Non-resident attributes**: The attribute content is stored in clusters elsewhere on disk. The MFT entry contains a **runlist** (data runs) that describes which clusters hold the data.
   177→
   178→**Attribute Header Format** (first 16 bytes common to both):
   179→```
   180→Offset  Size  Field
   181→0       4     Attribute type (e.g., 0x80 for $DATA)
   182→4       4     Total length of attribute
   183→8       1     Non-resident flag (0=resident, 1=non-resident)
   184→9       1     Name length
   185→10      2     Offset to name
   186→12      2     Flags (compressed, encrypted, sparse)
   187→14      2     Attribute ID
   188→```
   189→
   190→**Resident header** (additional bytes 16-23):
   191→```
   192→16      4     Length of attribute content
   193→20      2     Offset to attribute content
   194→22      1     Indexed flag
   195→23      1     Padding
   196→```
   197→
   198→**Non-resident header** (additional bytes 16-63):
   199→```
   200→16      8     Starting VCN
   201→24      8     Ending VCN
   202→32      2     Offset to data runs
   203→34      2     Compression unit size
   204→40      8     Allocated size
   205→48      8     Actual size
   206→56      8     Initialized size
   207→```
   208→
   209→#### 2.1.6 Data Runs (Runlists)
   210→
   211→Data runs encode the cluster allocation for non-resident attributes. The format is:
   212→
   213→1. A header byte where the **low nibble** = number of bytes for the run length, and the **high nibble** = number of bytes for the run offset.
   214→2. The run length bytes (unsigned, little-endian).
   215→3. The run offset bytes (signed, little-endian, relative to the previous run's starting cluster).
   216→
   217→**Example**: Runlist bytes `11 05 30 21 02 A4 03 21 04 64 FC`
   218→
   219→- `11`: 1-byte length, 1-byte offset
   220→- `05`: Run length = 5 clusters
   221→- `30`: Offset = 0x30 = 48 (absolute, first run) → clusters 48-52
   222→
   223→- `21`: 2-byte length, 1-byte offset
   224→- `02`: Run length = 2 clusters
   225→- `A4 03`: Offset = 0x03A4 = 932 (signed, relative to previous) → 48 + 932 = 980 → clusters 980-981
   226→
   227→- `21`: 2-byte length, 1-byte offset
   228→- `04`: Run length = 4 clusters
   229→- `64 FC`: Offset = 0xFC64 as signed 16-bit = -924 (relative) → 980 + (-924) = 56 → clusters 56-59
   230→
   231→The runlist is terminated by a `0x00` byte.
   232→
   233→### 2.2 NTFS Recovery Specifics
   234→
   235→#### 2.2.1 Deleted File Detection
   236→
   237→When a file is deleted on NTFS:
   238→1. The "in-use" bit in the MFT entry header is cleared.
   239→2. The $STANDARD_INFORMATION and $FILE_NAME attributes may be preserved.
   240→3. The $DATA attribute's runlist may be preserved (if the MFT entry is not reused).
   241→4. The clusters referenced by the runlist are marked as free in $Bitmap.
   242→
   243→**Key insight**: Unlike FAT, NTFS does not immediately zero out the MFT entry's data runs when a file is deleted. The runlist is preserved until the MFT entry is overwritten or the clusters are reused. This makes NTFS recovery highly reliable for recently deleted files.
   244→
   245→#### 2.2.2 $MFT Mirror
   246→
   247→$MFTMirr (MFT entry 1) contains a copy of the first 4 MFT entries ($MFT, $MFTMirr, $LogFile, $Volume). If the beginning of the MFT is corrupted, the mirror can be used to recover these critical entries. However, the mirror is only updated periodically, so it may be slightly stale.
   248→
   249→#### 2.2.3 $LogFile (Journal)
   250→
   251→The NTFS $LogFile is a circular journal that records all filesystem transactions. It contains:
   252→- **Restart area**: Contains checkpoint information for mount/umount state.
   253→- **Log records**: Record operations like creating files, extending attributes, updating directory indices.
   254→
   255→Recovery tools can parse $LogFile to:
   256→- Find recent file operations that may not yet be reflected in the on-disk MFT.
   257→- Recover information about recently deleted files.
   258→- Determine the last consistent filesystem state.
   259→
   260→DMDE specifically supports "process FS journal" option to include $LogFile information in reconstruction.
   261→
   262→#### 2.2.4 INDX Attributes (Directory Indexing)
   263→
   264→NTFS directories are implemented as B-trees. When a directory is large enough, it uses:
   265→- **$INDEX_ROOT** (always resident): The root of the B-tree.
   266→- **$INDEX_ALLOCATION** (non-resident): Contains the index blocks (INDX records).
   267→- **$BITMAP**: Tracks which index blocks are in use.
   268→
   269→INDX records contain file references (MFT number + sequence number) and file name information. When a file is deleted, the INDX entry may be marked as deleted but the entry is often preserved in the index leaf until the B-tree is rebalanced.
   270→
   271→**Recovery use**: Even when MFT entries are damaged, INDX records can be used to reconstruct directory structure. DMDE's "auto INDX processing" and "full INDX processing" features leverage this.
   272→
   273→#### 2.2.5 Handling Corrupted MFT
   274→
   275→Recovery strategies for corrupted MFT:
   276→
   277→1. **MFT scan**: Scan the entire disk for MFT entry signatures ("FILE" / 0x46494C45). Each valid MFT entry has a known structure that can be validated.
   278→
   279→2. **Sequential MFT enumeration**: Start from the MFT start offset (found in $Boot) and read entries sequentially. If an entry is corrupted (signature "BAAD"), skip it and continue.
   280→
   281→3. **$MFTMirr recovery**: Use the mirror to recover the first 4 critical entries.
   282→
   283→4. **INDX-based reconstruction**: Parse all INDX records to find file references, then attempt to locate the corresponding MFT entries.
   284→
   285→5. **$LogFile analysis**: Parse the journal to find recent file operations and MFT entry changes.
   286→
   287→6. **Attribute list traversal**: For files with $ATTRIBUTE_LIST, follow the attribute list to find all MFT entries that belong to the same file.
   288→
   289→7. **Shifted MFT records**: After a volume resize or corruption, MFT records may be shifted from their expected positions. DMDE's "Include Shifted" option handles this.
   290→
   291→8. **File carving as last resort**: If MFT is completely destroyed, fall back to signature-based carving.
   292→
   293→### 2.3 Common NTFS Failure Modes
   294→
   295→| Failure Mode | Cause | Recovery Approach |
   296→|---|---|---|
   297→| MFT entry corruption | Bad sectors, crash during write | MFT scan, $MFTMirr, INDX recovery |
   298→| MFT header corruption | Boot sector damage | Backup boot sector, GPT partition recovery |
   299→| $Bitmap corruption | Crash, malware | Scan all MFT entries to rebuild bitmap |
   300→| Runlist corruption | Bad sectors in MFT entry | Partial runlist + file carving for remainder |
   301→| Directory index corruption | B-tree damage | INDX scan, $LogFile analysis |
   302→| Partition table loss | Accidental format, malware | Surface scan for $Boot or MFT signatures |
   303→| Encrypted files (EFS) | Lost certificate | Usually unrecoverable without key backup |

   307→## 3. APFS Parser Design
   308→
   309→### 3.1 APFS Architecture Overview
   310→
   311→APFS (Apple File System) is a fundamentally different design from HFS+. Key differences:
   312→- **Copy-on-Write (CoW)**: All changes are written to new blocks, never overwriting in place. This makes APFS especially flash-friendly but complicates recovery.
   313→- **Container-based**: APFS uses a container model where a single container can hold multiple volumes.
   314→- **B-tree based**: Most metadata is stored in B-trees with a specific structure (b-tree nodes with btrailer).
   315→- **Encryption**: Native encryption support with per-volume or per-file encryption.
   316→- **Snapshots**: Built-in support for point-in-time snapshots.
   317→
   318→### 3.2 On-Disk Structure
   319→
   320→```
   321→┌─────────────────────────────────────────────────┐
   322→│              APFS Container                      │
   323→│  ┌───────────────────────────────────────────┐  │
   324→│  │  NX Superblock (Container Superblock)      │  │
   325→│  │  - Magic: 0x4253584E ("NXSB")              │  │
   326→│  │  - Block size, block count                 │  │
   327→│  │  - Pointers to: Object Map, B-tree         │  │
   328→│  │  - Volume superblock offsets               │  │
   329→│  ├───────────────────────────────────────────┤  │
   330→│  │  Object Map (OMAP)                         │  │
   331→│  │  - Maps virtual OIDs to physical blocks    │  │
   332→│  │  - Enables CoW: new versions get new OIDs  │  │
   333→│  ├───────────────────────────────────────────┤  │
   334→│  │  Volume Superblock (APSBSuperblock)        │  │
   335→│  │  - Magic: 0x41504653 ("APFS")              │  │
   336→│  │  - Root file system tree OID               │  │
   337→│  │  - Extent reference tree OID               │  │
   338→│  │  - Snapshot metadata tree OID              │  │
   339→│  │  - Encryption state                        │  │
   340→│  ├───────────────────────────────────────────┤  │
   341→│  │  B-Tree (File/Folder Tree)                 │  │
   342→│  │  - Directory structure as B-tree nodes      │  │
   343→│  │  - Each node has btrailer (checksum)       │  │
   344→│  │  - Leaf nodes contain file/folder records  │  │
   345→│  ├───────────────────────────────────────────┤  │
   346→│  │  Extent Reference Tree                     │  │
   347→│  │  - Maps file IDs to physical extent info   │  │
   348→│  │  - Separate from file/folder B-tree        │  │
   349→│  │  - Contains physical block references      │  │
   350→│  ├───────────────────────────────────────────┤  │
   351→│  │  Snapshots Metadata Tree                   │  │
   352→│  │  - Point-in-time snapshots of volumes      │  │
   353→│  │  - References to previous tree versions    │  │
   354→│  └───────────────────────────────────────────┘  │
   355→└─────────────────────────────────────────────────┘
   356→```
   357→
   358→### 3.3 Key APFS Structures
   359→
   360→#### 3.3.1 NX Superblock (Container Superblock)
   361→- **Magic**: 0x4253584E ("NXSB")
   362→- Contains the block size, total block count, and features flags.
   363→- Points to the Object Map (OMAP) which maps virtual object IDs (OIDs) to physical block addresses.
   364→- Contains an array of volume superblock physical OIDs.
   365→- Includes a checkpoint area for CoW consistency.
   366→
   367→#### 3.3.2 Object Map (OMAP)
   368→The OMAP is crucial for APFS's CoW mechanism. It maps virtual OIDs to physical block numbers. When a block is modified:
   369→1. A new block is allocated at a new physical location.
   370→2. The OMAP is updated to map the virtual OID to the new physical block.
   371→3. The old physical block becomes a free block (or is retained by a snapshot).
   372→
   373→For recovery, the OMAP history can be used to find previous versions of metadata blocks.
   374→
   375→#### 3.3.3 B-Tree Nodes
   376→APFS B-trees have a specific structure:
   377→- **Node header**: Contains the node type (leaf, index, root), level, and key/count information.
   378→- **Keys and values**: Stored in a table-of-contents layout.
   379→- **btrailer**: Every B-tree node has a trailing structure (btrailer) that contains:
   380→  - A checksum (Fletcher-64) for integrity verification.
   381→  - The node's object identifier.
   382→  - The transaction ID when the node was written.
   383→
   384→For recovery, the btrailer checksum is used to validate nodes. The transaction ID helps determine the chronological order of nodes.
   385→
   386→#### 3.3.4 Extent References
   387→Unlike HFS+ where the catalog file contains extent information, APFS stores extent references in a separate B-tree. Each extent reference contains:
   388→- The file's virtual OID.
   389→- The logical offset within the file.
   390→- The physical block number and length.
   391→- Reference count (for CoW clones).
   392→
   393→**Recovery implication**: To recover a file, you must first find it in the file/folder B-tree, then look up its extents in the extent reference tree. This two-step process is more complex than HFS+.
   394→
   395→#### 3.3.5 APFS Snapshots
   396→Snapshots are point-in-time copies of the volume's metadata. They work by:
   397→1. Creating a new volume superblock that references the same OMAP.
   398→2. The OMAP preserves the old virtual-to-physical mappings.
   399→3. New writes go to new blocks, while old blocks are preserved by the snapshot.
   400→
   401→Recovery tools can use snapshots to recover previous file versions, even if the files were deleted from the live volume.
   402→
   403→### 3.4 What Makes APFS Recovery Harder Than HFS+
   404→
   405→| Factor | HFS+ | APFS |
   406→|--------|------|------|
   407→| **Encryption** | Optional FileVault 2 (whole-disk) | Native per-file or per-volume encryption |
   408→| **Metadata location** | Catalog file (single B-tree) | Multiple B-trees (file tree, extent tree, snapshot tree) |
   409→| **Block mapping** | Direct extent records in catalog | Indirect via OMAP + extent reference tree |
   410→| **CoW** | No (overwrites in place) | Yes (writes to new blocks) |
   411→| **Deletion** | Catalog node removed, extent freed | B-tree nodes replaced, old blocks may be retained by snapshots or freed |
   412→| **Checksums** | Limited | Fletcher-64 on every B-tree node |
   413→| **TRIM support** | Basic | Aggressive (immediately frees blocks) |
   414→| **Documentation** | Well-documented | Official spec under NDA, partially reverse-engineered |
   415→
   416→**Encryption challenges**: APFS encryption is deeply integrated. Volumes can be encrypted with different keys. Even if the container superblock is found, the encryption keys may be protected by the user's passphrase or hardware SEP (Secure Enclave Processor). Without the key, data is unrecoverable.
   417→
   418→**TRIM/UNMAP**: APFS aggressively sends TRIM commands to SSDs, which causes the SSD controller to erase freed blocks. This makes recovery of deleted files much harder on SSDs compared to HDDs.
   419→
   420→**CoW complexity**: Because APFS writes new blocks for every change, the on-disk state contains many old versions of metadata. Recovery tools must parse the OMAP to determine which version is current, and they can potentially access old versions through snapshot references.
   421→
   422→### 3.5 APFS Recovery Strategies
   423→
   424→1. **NX Superblock scan**: Search for the NXSB magic number (0x4253584E) to locate the container superblock.
   425→2. **OMAP traversal**: Parse the OMAP to map virtual OIDs to physical blocks.
   426→3. **B-tree validation**: Verify each B-tree node using its btrailer checksum.
   427→4. **Extent tree reconstruction**: If the extent reference tree is damaged, scan for extent reference records.
   428→5. **Snapshot recovery**: Check for snapshot metadata trees that reference previous versions of the volume.
   429→6. **Block-level carving**: If all metadata is lost, fall back to file carving on the raw block device.

   433→## 4. EXT4 Parser Design
   434→
   435→### 4.1 EXT4 On-Disk Layout
   436→
   437→An EXT4 filesystem is divided into **block groups**. Each block group is a self-contained unit:
   438→
   439→```
   440→┌──────────────────────────────────────────────────────────────┐
   441→│ Block Group 0                                                 │
   442→│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
   443→│  │  Superblock   │  │  Group Desc  │  │  Data Block  │  ...  │
   444→│  │  (primary)    │  │  Table       │  │  Bitmap      │       │
   445→│  └──────────────┘  └──────────────┘  └──────────────┘       │
   446→│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
   447→│  │  Inode Bitmap │  │  Inode Table │  │  Data Blocks │  ...  │
   448→│  └──────────────┘  └──────────────┘  └──────────────┘       │
   449→├──────────────────────────────────────────────────────────────┤
   450→│ Block Group 1                                                 │
   451→│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
   452→│  │  Superblock   │  │  Group Desc  │  │  ...          │  ... │
   453→│  │  (backup)     │  │  Table       │  │              │       │
   454→│  └──────────────┘  └──────────────┘  └──────────────┘       │
   455→├──────────────────────────────────────────────────────────────┤
   456→│ ...                                                           │
   457→└──────────────────────────────────────────────────────────────┘
   458→```
   459→
   460→### 4.2 Key Structures
   461→
   462→#### 4.2.1 Superblock
   463→
   464→The superblock contains critical filesystem parameters:
   465→- **Magic number**: 0xEF53 (at offset 0x38)
   466→- **Block size**: Stored as log2(size) - 10 (so 0 = 1024, 1 = 2048, 2 = 4096)
   467→- **Block count**: Total number of blocks
   468→- **Inode count**: Total number of inodes
   469→- **Blocks per group**: Typically 8 * block_size (32768 for 4KB blocks)
   470→- **Inodes per group**: Number of inodes per block group
   471→- **Feature flags**: Compatible, incompatible, and read-only feature flags
   472→- **Journal inode**: Inode number of the journal (usually 8)
   473→- **Journal backup**: Superblock may contain journal info
   474→
   475→Backup superblocks are stored at the beginning of block groups 1, 5, 7, 9, 25, 27, 49, etc. (powers of 3, 5, 7 times the block group size).
   476→
   477→#### 4.2.2 Block Group Descriptors
   478→
   479→Each block group has a descriptor (32 or 64 bytes) containing:
   480→- Block bitmap location
   481→- Inode bitmap location
   482→- Inode table location
   483→- Free block count
   484→- Free inode count
   485→- Used directory count
   486→
   487→The group descriptor table is stored immediately after the superblock. With the 64-bit feature, the descriptor size expands to 64 bytes.
   488→
   489→#### 4.2.3 Inode Table
   490→
   491→Each block group contains an inode table. Each inode is typically 256 bytes (can be larger) and contains:
   492→- **File mode**: Type and permissions
   493→- **Owner UID/GID**
   494→- **Size**: File size in bytes
   495→- **Timestamps**: Access, modification, change, deletion (if available)
   496→- **Link count**: Number of hard links (0 = deleted)
   497→- **Blocks count**: Number of 512-byte blocks allocated
   498→- **Flags**: Various flags including extent flag, inline data flag
   499→- **Extent tree root** or **block pointers**: Location of file data
   500→
   501→#### 4.2.4 Extent Trees
   502→
   503→EXT4 uses extent trees (instead of the direct/indirect block pointers of EXT2/3) to map file data:
   504→
   505→```
   506→Extent Tree:
   507→┌─────────────────────────┐
   508→│  Root Node (in inode)    │
   509→│  ┌─────────────────────┐│
   510→│  │  Extent Header       ││
   511→│  │  - depth, entries    ││
   512→│  ├─────────────────────┤│
   513→│  │  Extent Index 1      ││  → Points to child node
   514→│  │  Extent Index 2      ││  → Points to child node
   515→│  └─────────────────────┘│
   516→└─────────────────────────┘
   517→         │
   518→         ▼
   519→┌─────────────────────────┐
   520→│  Leaf Node              │
   521→│  ┌─────────────────────┐│
   522→│  │  Extent Header       ││
   523→│  ├─────────────────────┤│
   524→│  │  Extent 1:           ││
   525→│  │   - logical block    ││
   526→│  │   - length           ││
   527→│  │   - physical block   ││
   528→│  │  Extent 2:           ││
   529→│  │   - logical block    ││
   530→│  │   - length           ││
   531→│  │   - physical block   ││
   532→│  └─────────────────────┘│
   533→└─────────────────────────┘
   534→```
   535→
   536→An extent describes a contiguous range of blocks:
   537→- **Logical block**: Starting file offset (in blocks)
   538→- **Length**: Number of blocks in this extent (up to 32768)
   539→- **Physical block**: Starting block on disk
   540→
   541→### 4.3 EXT4 Recovery Specifics
   542→
   543→#### 4.3.1 Deleted File Handling
   544→
   545→When a file is deleted on EXT4:
   546→1. The directory entry is removed (the inode number is zeroed out).
   547→2. The inode's link count is decremented (to 0 if no other hard links).
   548→3. **The extent tree pointers in the inode are zeroed out.** This is the critical difference from NTFS — EXT4 does not preserve the extent information for deleted files.
   549→4. The blocks are freed in the block bitmap.
   550→5. The inode is marked as free in the inode bitmap.
   551→
   552→**This means**: Unlike NTFS, EXT4 deleted file recovery cannot rely on the inode's extent tree. The data blocks themselves remain on disk until overwritten, but the mapping from file to blocks is lost.
   553→
   554→#### 4.3.2 Journal Replay
   555→
   556→The EXT4 journal (usually inode 8) records filesystem transactions. It contains:
   557→- **Journal superblock**: Contains journal parameters.
   558→- **Descriptor blocks**: Describe the following data blocks.
   559→- **Data blocks**: Copies of filesystem blocks before they were modified.
   560→- **Commit blocks**: Mark complete transactions.
   561→
   562→Recovery tools can:
   563→1. Parse the journal to find copies of metadata blocks (inodes, directory entries, extent trees) that were modified or deleted.
   564→2. Reconstruct deleted file extent trees from journal data.
   565→3. Use the journal to find the last consistent filesystem state.
   566→
   567→#### 4.3.3 Recovery Strategies for Deleted Files
   568→
   569→1. **Journal-based recovery**: Parse the journal for copies of deleted inodes and directory entries. This is the most reliable method for EXT4.
   570→2. **Block group scanning**: Scan inode tables for inodes with deletion timestamps set but data still present.
   571→3. **Directory entry carving**: Scan data blocks for directory entry structures that reference deleted inodes.
   572→4. **Extent tree carving**: Search for extent tree structures in journal data blocks.
   573→5. **File carving**: If all metadata is lost, fall back to signature-based carving.
   574→
   575→#### 4.3.4 Superblock Recovery
   576→
   577→If the primary superblock is corrupted:
   578→1. Use backup superblocks at known block group offsets.
   579→2. Calculate backup positions: Block groups at powers of 3, 5, 7 times the block group descriptor size.
   580→3. Verify each backup superblock's magic number (0xEF53) and checksum.
   581→

   583→
   584→## 5. FAT/exFAT Parser Design
   585→
   586→### 5.1 FAT32 Structure
   587→
   588→#### 5.1.1 Volume Layout
   589→
   590→```
   591→┌────────────────────────────┐
   592→│  Boot Sector (Sector 0)    │
   593→│  - OEM name, bytes/sector  │
   594→│  - Sectors/cluster         │
   595→│  - Reserved sectors        │
   596→│  - Number of FATs          │
   597→│  - Root dir cluster        │
   598→│  - FSInfo sector           │
   599→├────────────────────────────┤
   600→│  FSInfo Sector             │
   601→│  - Free cluster count      │
   602→│  - Next free cluster       │
   603→├────────────────────────────┤
   604→│  Reserved Sectors          │
   605→├────────────────────────────┤
   606→│  FAT1 (File Allocation Tab)│
   607→│  - Cluster chain entries   │
   608→│  - 4 bytes per cluster     │
   609→│  - 0x0FFFFFF8 = end of     │
   610→│    chain                   │
   611→│  - 0x00000000 = free       │
   612→│  - 0x0FFFFFF7 = bad        │
   613→├────────────────────────────┤
   614→│  FAT2 (Backup Copy)        │
   615→├────────────────────────────┤
   616→│  Root Directory            │
   617→│  - Directory entries       │
   618→├────────────────────────────┤
   619→│  Data Area                 │
   620→│  - Clusters 2, 3, 4, ...  │
   621→└────────────────────────────┘
   622→```
   623→
   624→#### 5.1.2 FAT Table Entries
   625→
   626→The FAT (File Allocation Table) is an array of cluster entries. Each entry contains:
   627→- **0x00000000**: Free cluster
   628→- **0x0FFFFFF7**: Bad cluster
   629→- **0x0FFFFFF8-0x0FFFFFFF**: End of chain (last cluster of a file)
   630→- **Any other value**: Next cluster number in the chain
   631→
   632→To read a file, you follow the cluster chain from the starting cluster (stored in the directory entry) through the FAT until you reach an end-of-chain marker.
   633→
   634→#### 5.1.3 Directory Entries
   635→
   636→Each 32-byte directory entry contains:
   637→- **Byte 0**: First character of filename (0x00 = never used, 0xE5 = deleted)
   638→- **Bytes 1-10**: Remaining characters of filename (8.3 format)
   639→- **Byte 11**: Attributes (read-only, hidden, system, volume label, directory, archive)
   640→- **Bytes 20-21**: High word of starting cluster (FAT32 only)
   641→- **Bytes 26-27**: Low word of starting cluster
   642→- **Bytes 28-31**: File size in bytes
   643→
   644→#### 5.1.4 Long Filename (LFN) Entries
   645→
   646→LFN entries use 32-byte directory entries with attribute 0x0F:
   647→- **Byte 0**: Sequence number (0x01-0x14, 0x40 | n for last entry)
   648→- **Bytes 1-10**: Characters 1-5 of name (UTF-16LE)
   649→- **Byte 11**: Attribute 0x0F
   650→- **Byte 12**: Type (0x00)
   651→- **Byte 13**: Checksum of 8.3 name
   652→- **Bytes 14-25**: Characters 6-11 of name (UTF-16LE)
   653→- **Bytes 26-27**: Starting cluster (always 0)
   654→- **Bytes 28-31**: Characters 12-13 of name (UTF-16LE)
   655→
   656→LFN entries are stored in reverse order before the 8.3 entry.
   657→
   658→### 5.2 exFAT Structure
   659→
   660→#### 5.2.1 Key Differences from FAT32
   661→
   662→exFAT was designed for flash drives and large files. Key differences:
   663→- No FAT table for cluster chains (uses a different approach)
   664→- Support for files > 4GB
   665→- No journaling
   666→- Larger cluster sizes (up to 32MB)
   667→- Free space bitmap instead of FAT
   668→
   669→#### 5.2.2 exFAT Volume Layout
   670→
   671→```
   672→┌────────────────────────────┐
   673→│  Boot Sector (Sector 0)    │
   674→│  - Volume length, FAT off  │
   675→│  - Cluster heap offset     │
   676→│  - Cluster count           │
   677→│  - Root dir cluster        │
   678→├────────────────────────────┤
   679→│  Extended Boot Sectors     │
   680→│  (Sectors 1-7)             │
   681→├────────────────────────────┤
   682→│  OEM Parameters            │
   683→├────────────────────────────┤
   684→│  Reserved                  │
   685→├────────────────────────────┤
   686→│  FAT (single copy)         │
   687→│  - Cluster chain entries   │
   688→│  - Used for fragmented     │
   689→│    files only              │
   690→├────────────────────────────┤
   691→│  Allocation Bitmap         │
   692→│  - 1 bit per cluster       │
   693→│  - 1 = allocated, 0 = free │
   694→├────────────────────────────┤
   695→│  Up-case Table             │
   696→│  - Case conversion table   │
   697→│  - Required for filename   │
   698→│    comparisons             │
   699→├────────────────────────────┤
   700→│  Cluster Heap (Data Area)  │
   701→│  - Contains directories    │
   702→│    and files               │
   703→└────────────────────────────┘
   704→```
   705→
   706→#### 5.2.3 exFAT Directory Entries
   707→
   708→exFAT uses a different directory entry format with three types of entries per file:
   709→
   710→1. **File Directory Entry** (primary, critical):
   711→   - Entry type: 0x85
   712→   - Attribute flags
   713→   - Number of secondary entries
   714→   - File name hash
   715→   - File size
   716→
   717→2. **Stream Extension Directory Entry** (secondary, critical):
   718→   - Entry type: 0xC0
   719→   - Flags (allocation possible, no FAT chain)
   720→   - First cluster
   721→   - Data length
   722→   - If "no FAT chain" flag is set, the file is contiguous and the FAT is not used.
   723→
   724→3. **File Name Directory Entry** (secondary, critical):
   725→   - Entry type: 0xC1
   726→   - File name characters (UTF-16LE, up to 15 chars per entry)
   727→   - Multiple entries may be needed for long filenames
   728→
   729→### 5.3 FAT/exFAT Recovery Specifics
   730→
   731→#### 5.3.1 Deleted File Detection
   732→
   733→**FAT32**: When a file is deleted:
   734→1. The first byte of the 8.3 directory entry is replaced with 0xE5.
   735→2. The FAT chain entries are zeroed out (clusters marked as free).
   736→3. The directory entry data is otherwise preserved.
   737→4. LFN entries may have their first byte replaced with 0xE5 as well.
   738→
   739→**exFAT**: When a file is deleted:
   740→1. The entry type byte is inverted (0x85 → 0x05, 0xC0 → 0x40, 0xC1 → 0x41).
   741→2. The allocation bitmap is updated to mark clusters as free.
   742→3. The stream extension and file name entries may be preserved.
   743→
   744→#### 5.3.2 Recovery Challenges
   745→
   746→- **FAT chain loss**: On FAT32, the cluster chain is destroyed when a file is deleted. For fragmented files, this means the tool must guess the correct order of clusters. For contiguous files, the starting cluster + file size is sufficient.
   747→- **FAT table selection**: FAT32 has two copies of the FAT table. Recovery tools may try both to determine which is more reliable. DMDE allows selecting FAT1, FAT2, or both, with an option to check for bad sectors.
   748→- **exFAT single FAT**: exFAT has only one FAT table, and it cannot be properly tested (values are correctly defined for fragmented file chains only).
   749→- **Overwritten directory entries**: If directory entries are overwritten, the tool must scan for remaining directory entries or use file carving.

   753→## 6. File Carving / Signature Scanning
   754→
   755→### 6.1 What is File Carving?
   756→
   757→File carving is the process of recovering files from raw storage data **without using filesystem metadata**. It relies on knowledge of file format structures to identify and extract files.
   758→
   759→### 6.2 Carving Methods
   760→
   761→#### 6.2.1 Header-Footer Carving
   762→
   763→The simplest method:
   764→1. Search for a file's **magic number** (header signature) in the raw data.
   765→2. Search for the corresponding **footer signature**.
   766→3. Extract everything between the header and footer.
   767→
   768→**Example**: JPEG files start with `FF D8 FF` and end with `FF D9`.
   769→
   770→**Limitations**:
   771→- Only works for contiguous files.
   772→- May produce false positives if footer signatures appear in other data.
   773→- Cannot determine the correct file size for formats without a footer.
   774→- Fails for fragmented files.
   775→
   776→#### 6.2.2 Header-Size Carving
   777→
   778→Some file formats embed the file size in the header:
   779→1. Search for the header signature.
   780→2. Parse the size field from the header.
   781→3. Extract the specified number of bytes.
   782→
   783→**Example**: PNG files have a length field in the IHDR chunk, and the file size can be determined from the chunk structure.
   784→
   785→**Limitations**:
   786→- The size field may be corrupted.
   787→- The size field may represent the uncompressed size rather than the on-disk size.
   788→- Not all file formats include size information in the header.
   789→
   790→#### 6.2.3 Bifragment Gap Carving
   791→
   792→For files that are split into exactly **two fragments** with a gap between them:
   793→
   794→1. Find the header signature.
   795→2. Find the footer signature.
   796→3. Assume the file consists of two contiguous blocks with a gap between them.
   797→4. Try all possible gap sizes and positions.
   798→5. Validate each candidate by parsing the file structure.
   799→
   800→**Example**: A JPEG file split into two fragments at clusters 100-104 and 200-203, with clusters 105-199 being a gap.
   801→
   802→**Validation**: For JPEG, validate by checking that the Huffman tables, restart markers, and end-of-image marker are all at expected positions.
   803→
   804→**Limitations**:
   805→- Only works for files with exactly two fragments.
   806→- The number of possible gap positions grows with the gap size.
   807→- Validation is file-format-specific.
   808→
   809→#### 6.2.4 Sequential Carving
   810→
   811→For heavily fragmented files:
   812→1. Find all blocks that could belong to the file (based on content analysis).
   813→2. Try different orderings of blocks.
   814→3. Validate each candidate ordering.
   815→
   816→**Limitations**:
   817→- Computationally expensive (NP-hard in the general case).
   818→- Validation is the bottleneck.
   819→- Not practical for large files with many fragments.
   820→
   821→#### 6.2.5 Smart Carving (Object Validation)
   822→
   823→A more sophisticated approach:
   824→1. **Pre-processing**: Identify all blocks that could potentially belong to each file type.
   825→2. **Collation**: Group blocks by file type and sort by block number.
   826→3. **Reassembly**: Use file-format-specific parsers to validate and assemble fragments.
   827→4. **Validation**: For each candidate file, perform deep structural validation:
   828→   - JPEG: Validate Huffman tables, restart markers, scan structure
   829→   - PDF: Validate cross-reference table, object structure
   830→   - ZIP: Validate local file headers, central directory
   831→   - DOCX: Validate ZIP structure + XML content
   832→
   833→This approach is used by tools like Scalpel, PhotoRec, and Foremost.
   834→
   835→### 6.3 Common File Signatures (Magic Numbers)
   836→
   837→| File Type | Header Signature | Footer Signature |
   838→|-----------|-----------------|-----------------|
   839→| JPEG | `FF D8 FF E0` / `FF D8 FF E1` | `FF D9` |
   840→| PNG | `89 50 4E 47 0D 0A 1A 0A` | `49 45 4E 44 AE 42 60 82` |
   841→| GIF | `47 49 46 38 37 61` / `47 49 46 38 39 61` | `00 3B` |
   842→| PDF | `25 50 44 46` | `25 25 45 4F 46` |
   843→| ZIP | `50 4B 03 04` | `50 4B 05 06` |
   844→| RAR | `52 61 72 21 1A 07 00` | — |
   845→| DOCX/XLSX/PPTX | `50 4B 03 04` (ZIP) | `50 4B 05 06` |
   846→| DOC (OLE2) | `D0 CF 11 E0 A1 B1 1A E1` | — |
   847→| AVI | `52 49 46 46 .. .. .. .. 41 56 49 20` | — |
   848→| MP4 | `.. .. .. .. 66 74 79 70` | — |
   849→| SQLite | `53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00` | — |
   850→
   851→### 6.4 File Length Detection
   852→
   853→Determining file length is one of the hardest problems in carving:
   854→
   855→1. **Embedded size**: Some formats (PNG, TIFF, ZIP, RAR) include size information in the header.
   856→2. **Footer detection**: Some formats (JPEG, GIF) have explicit end markers.
   857→3. **Structural parsing**: Parse the file structure to determine logical boundaries (PDF, DOCX).
   858→4. **Heuristic detection**: For formats without size or footer, use content analysis to estimate the end.
   859→5. **Cluster alignment**: If the file is contiguous, the end is at the starting cluster + ceil(file_size / cluster_size) * cluster_size.
   860→
   861→### 6.5 Limitations of File Carving
   862→
   863→- **Fragmentation**: The biggest challenge. No file carver can automatically reassemble heavily fragmented files with 100% accuracy.
   864→- **False positives**: Magic numbers can appear in random data, leading to false detections.
   865→- **File naming**: Carved files lose their original names and directory structure.
   866→- **No metadata**: Carved files lose timestamps, permissions, and other metadata.
   867→- **Encrypted/compressed files**: Cannot be carved without the key or decompression algorithm.
   868→- **Performance**: Scanning an entire disk for signatures is slow. Optimizations include block-level caching and parallel processing.
   869→- **SSD TRIM**: On SSDs, TRIM commands may erase freed blocks, making carving impossible.

   873→## 7. Filesystem Reconstruction
   874→
   875→### 7.1 Overview
   876→
   877→Filesystem reconstruction is the process of rebuilding a damaged or partially destroyed filesystem's directory tree and file metadata. This is the core capability that distinguishes professional tools like R-Studio and DMDE from simple file carvers.
   878→
   879→### 7.2 DMDE's Reconstruction Approach
   880→
   881→Based on DMDE's documentation, the reconstruction process works as follows:
   882→
   883→1. **Full Scan**: The tool performs a full scan of the disk, searching for:
   884→   - Filesystem metadata fragments (MFT entries, INDX records, directory entries, etc.)
   885→   - Boot sector / superblock copies
   886→   - Journal data
   887→   - Any other recognizable filesystem structures
   888→
   889→2. **FS Fragment Classification**: Found fragments are grouped by their probability of belonging to the current volume:
   890→   - **Best/Correct**: Most likely and likely to belong to the open volume
   891→   - **Related**: Probably related to other versions of this volume (e.g., before a format)
   892→   - **Unknown**: Relevant volume could not be detected
   893→   - **Extraneous**: Relevant to a different volume
   894→   - **Small (extra found)**: Too small for statistical analysis
   895→   - **Disabled**: Incompatible due to different filesystem parameters
   896→
   897→3. **Virtual File System Assembly**: The tool assembles a virtual directory tree from the collected fragments:
   898→   - **NTFS**: Merges MFT entries, INDX records, and $LogFile data to build the directory tree.
   899→   - **FAT/exFAT**: Uses FAT table copies and directory entries to reconstruct the file structure.
   900→   - **Other filesystems**: Uses filesystem-specific metadata.
   901→
   902→4. **Reconstruction Quality Control**: The user can adjust the reconstruction using:
   903→   - **More/Less Results** buttons: Increase or decrease the number of files included in the reconstruction.
   904→   - **Advanced parameters**: For specialists to fine-tune the reconstruction.
   905→   - **Color indicators**: Show the quality and number of selected results.
   906→
   907→### 7.3 NTFS-Specific Reconstruction Heuristics
   908→
   909→#### 7.3.1 INDX Processing
   910→
   911→DMDE's INDX processing is a key differentiator:
   912→
   913→- **Auto INDX processing**: Uses information from INDX records on top of MFT data to reconstruct directory structure. This is slower but more accurate.
   914→- **Full INDX processing**: Forces INDX processing even when MFT data is available.
   915→- **INDX merging improvement**: Prevents possible wrong merging of directory branches by considering timestamps.
   916→
   917→When an MFT entry for a directory is damaged, its INDX records may still contain the file references. The tool can:
   918→1. Scan all INDX records.
   919→2. Build a parent-child relationship map from the INDX data.
   920→3. Merge this with the directory tree built from MFT entries.
   921→
   922→#### 7.3.2 Shifted MFT Records
   923→
   924→After a volume resize or corruption, MFT records may be shifted from their expected positions. The tool:
   925→1. Identifies MFT records at unexpected offsets.
   926→2. Maps them to their correct MFT numbers.
   927→3. Includes them in the reconstruction.
   928→
   929→#### 7.3.3 Extra Found Files
   930→
   931→The "Include Extra Found" option may include:
   932→- Files from MFT entries that don't clearly belong to the current volume.
   933→- Files with inconsistent metadata.
   934→- Files from orphaned MFT entries.
   935→
   936→This may contain more garbage but can help recover files that are not recoverable through other means.
   937→
   938→#### 7.3.4 Journal Processing
   939→
   940→The "Process FS journal" option includes information from the NTFS $LogFile:
   941→- Recent file operations that may not be reflected in the on-disk MFT.
   942→- Undo information for incomplete transactions.
   943→- File creation/deletion records.
   944→
   945→### 7.4 R-Studio's Reconstruction Approach
   946→
   947→R-Studio uses a similar approach but with some differences:
   948→
   949→1. **Known File Types (KFT)**: R-Studio maintains a database of known file types and their signatures. During a scan, it can identify files by their content even when metadata is missing.
   950→
   951→2. **Extra Found Files**: R-Studio categorizes found files into:
   952→   - **Existing files**: Files with valid metadata and data.
   953→   - **Deleted files**: Files with metadata indicating deletion.
   954→   - **Extra found files**: Files found by carving or from damaged metadata.
   955→
   956→3. **Multi-pass scan**: R-Studio performs a quick scan first for existing metadata, then a deep scan for carving.
   957→
   958→4. **RAID reconstruction**: R-Studio can automatically detect RAID parameters (stripe size, order, parity) and reconstruct virtual RAID arrays.
   959→
   960→### 7.5 General Reconstruction Heuristics
   961→
   962→Common heuristics used by reconstruction engines:
   963→
   964→1. **Timestamp consistency**: Files in a directory should have timestamps that are reasonably consistent with the directory's creation time.
   965→2. **Parent-child validation**: Verify that a file's parent directory reference points to a valid directory.
   966→3. **Cluster allocation validation**: Check that file clusters don't overlap with other files or metadata areas.
   967→4. **Size consistency**: Compare the file size in the metadata with the actual data size.
   968→5. **Sequential MFT numbering**: NTFS MFT entries are typically allocated sequentially, so the MFT number can be used as a rough chronological ordering.
   969→6. **File type validation**: Verify that the file extension matches the file content (magic number).
   970→7. **Checksum validation**: Use filesystem checksums (APFS btrailer, ZFS checksums) to validate metadata integrity.
   971→8. **Bitmap cross-referencing**: Compare the allocation bitmap with the actual file allocations to detect inconsistencies.
   972→

   975→## 8. Raw Disk Reading
   976→
   977→### 8.1 Direct Disk Access Methods
   978→
   979→#### 8.1.1 Windows
   980→
   981→On Windows, raw disk access is achieved through:
   982→- **`CreateFile("\\\\.\\PhysicalDriveN")`**: Opens a raw handle to the physical disk.
   983→- **`ReadFile()`**: Reads sectors from the disk handle.
   984→- **`DeviceIoControl()` with `IOCTL_DISK_READ`**: Reads specific sectors.
   985→- **`IOCTL_SCSI_PASS_THROUGH`**: Sends raw SCSI commands to the disk.
   986→
   987→For USB drives, the USB mass storage protocol translates SCSI commands to USB bulk transfers. The USB bridge controller (e.g., JMicron, ASMedia, Prolific) handles the translation.
   988→
   989→#### 8.1.2 Linux
   990→
   991→On Linux, raw disk access is through:
   992→- **`/dev/sdX`**: Block device file for the entire disk.
   993→- **`/dev/sdXN`**: Block device file for partition N.
   994→- **`open()` + `read()`**: Direct sector reading.
   995→- **`ioctl()` with `SG_IO`**: SCSI Generic interface for sending SCSI commands.
   996→- **`hdparm`**: For ATA-specific commands (SMART, security, etc.).
   997→
   998→#### 8.1.3 macOS
   999→
  1000→On macOS, raw disk access uses:
  1001→- **`/dev/diskN`**: Block device file.
  1002→- **`/dev/rdiskN`**: Raw device file (no buffering).
  1003→- **`IOKit` framework**: For low-level device access.
  1004→- **`IOService`**: For ATA/SCSI command pass-through.
  1005→
  1006→### 8.2 ATA/SCSI Commands for Data Recovery
  1007→
  1008→| Command | ATA | SCSI | Purpose |
  1009→|---------|-----|------|---------|
  1010→| Read sectors | `READ DMA EXT` (0x25) | `READ(10)` (0x28) | Read data sectors |
  1011→| Read SMART data | `SMART READ DATA` (0xB0) | `READ ATTRIBUTE` | Get disk health info |
  1012→| Read DMA | `READ DMA EXT` | `READ(16)` | Read with DMA transfer |
  1013→| Identify device | `IDENTIFY DEVICE` (0xEC) | `INQUIRY` (0x12) | Get disk capabilities |
  1014→| Read NATIVE MAX | `READ NATIVE MAX ADDRESS` | — | Detect HPA (Host Protected Area) |
  1015→| Read DMA LOG | `READ LOG DMA EXT` | `LOG SENSE` | Read error logs |
  1016→| TRIM / UNMAP | `DATA SET MANAGEMENT` | `UNMAP` | Inform SSD of freed blocks |
  1017→
  1018→### 8.3 SATA vs USB Protocols
  1019→
  1020→**SATA (Serial ATA)**:
  1021→- Direct connection to the disk controller.
  1022→- Full ATA command set available.
  1023→- No protocol translation overhead.
  1024→- Supports NCQ (Native Command Queuing) for efficient read scheduling.
  1025→- Can access HPA (Host Protected Area) and DCO (Device Configuration Overlay).
  1026→
  1027→**USB Mass Storage**:
  1028→- USB bridge chip translates SCSI commands to ATA commands.
  1029→- Limited command set (SCSI subset only).
  1030→- Some ATA-specific commands (SMART, HPA, DCO) may not be available through the bridge.
  1031→- Bridge chips may have bugs or limitations in command translation.
  1032→- Some bridges have a 2TB limit (using 32-bit LBA instead of 64-bit).
  1033→- USB 3.0 provides sufficient bandwidth (5 Gbps) for most recovery operations.
  1034→
  1035→**Important for recovery**: When possible, connect the disk directly via SATA rather than USB. This provides:
  1036→- Full access to the ATA command set.
  1037→- Better error reporting.
  1038→- No USB bridge overhead or bugs.
  1039→- Access to HPA/DCO areas.
  1040→
  1041→### 8.4 Handling I/O Errors
  1042→
  1043→I/O errors are a common challenge in data recovery. Strategies include:
  1044→
  1045→#### 8.4.1 Error Recovery Hierarchy
  1046→
  1047→1. **Retry with OS**: Simple retry of the read operation. May succeed if the error was transient.
  1048→2. **ATA PASS-THROUGH**: Send a raw ATA read command with extended retry options.
  1049→3. **Partial read**: Read the sector in smaller chunks (e.g., 512 bytes at a time instead of 4096).
  1050→4. **Skip and continue**: Skip the bad sector and continue reading. Mark the sector as unreadable.
  1051→5. **Reverse read**: Read the disk from the end towards the beginning. This can sometimes work around mechanical issues.
  1052→6. **Hardware-specific**: Use vendor-specific commands (e.g., Seagate's `READ LONG` command) to read data even with ECC errors.
  1053→
  1054→#### 8.4.2 Disk Imaging Strategies
  1055→
  1056→Professional tools use adaptive imaging strategies:
  1057→
  1058→- **ddrescue**: A GNU tool that reads the disk in passes:
  1059→  - First pass: Read all easily readable sectors.
  1060→  - Second pass: Read sectors that failed, with smaller block sizes and more retries.
  1061→  - Third pass: Try to read individual sectors that still failed.
  1062→  - Uses a "mapfile" to track which sectors have been read and which have failed.
  1063→
  1064→- **DMDE's imaging**: Uses a similar approach with:
  1065→  - Configurable retry count and timeout.
  1066→  - Read-ahead optimization.
  1067→  - Skip count for consecutive errors.
  1068→  - Sector-by-sector reading for failed areas.
  1069→
  1070→- **DeepSpar Disk Imager**: A professional hardware-based imager that:
  1071→  - Connects directly to the disk via SATA/IDE.
  1072→  - Uses ATA commands directly, bypassing the OS.
  1073→  - Handles bad sectors with configurable retry strategies.
  1074→  - Can read sectors with ECC errors (ignoring the ECC check).
  1075→  - Has a built-in disk health monitor.
  1076→
  1077→- **PC-3000**: A professional hardware/software combination from ACE Lab that:
  1078→  - Provides full ATA/SCSI command control.
  1079→  - Can disable the disk's internal error correction.
  1080→  - Can read in "technological mode" (accessing firmware zones).
  1081→  - Can repair firmware issues on specific disk models.
  1082→
  1083→### 8.5 SAS/SCSI Considerations
  1084→
  1085→SAS (Serial Attached SCSI) drives present additional challenges:
  1086→- **Extended error reporting**: SAS/SCSI protocols have an extended error-reporting system providing more information on issues.
  1087→- **SCSI sense codes**: More detailed error information than ATA status codes.
  1088→- **Different command set**: SAS drives use SCSI commands, not ATA commands.
  1089→- **Enterprise features**: SAS drives may have additional features like T10 Protection Information (PI) and persistent reservations.
  1090→
  1091→### 8.6 SSD-Specific Considerations
  1092→
  1093→- **TRIM/UNMAP**: When a file is deleted, the OS sends TRIM commands to the SSD, which may erase the logical blocks. This makes recovery of deleted files on SSDs significantly harder.
  1094→- **Wear leveling**: SSD controllers use wear leveling algorithms that distribute writes across all physical blocks. This means the logical-to-physical mapping is not straightforward.
  1095→- **FTL (Flash Translation Layer)**: The SSD controller's firmware maps logical block addresses to physical flash pages. This mapping is proprietary and varies between SSD manufacturers.
  1096→- **Encryption**: Many modern SSDs use hardware encryption (SED - Self-Encrypting Drive). Even without a user password, the data is encrypted on the flash chips. Recovery requires the encryption key.
  1097→- **Read disturbance**: Reading the same flash block repeatedly can cause adjacent cells to flip, potentially corrupting data.
