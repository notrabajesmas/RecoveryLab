class=\"rc81accent\" href=\"https://blogs.oracle.com/linux/category/lnx-technologies\">Technologies</a>                        </div>\n\n                        <h1>Understanding Ext4 Disk Layout, Part 1</h1>\n                        <div class=\"blogtile-byline\">\n                            <span class=\"publishdate\">May 30, 2023</span>\n                            <span>17 minute read</span>\n                        </div>\n\n                        <div class=\"rc81sub\"><img src=\"https://blogs.oracle.com/linux/wp-content/themes/oracleredwoodblog/assets/images/default_avatar.jpg\" width=\"40\" alt=\"Profile picture of Srivathsa Dara\">\n        <span class=\"blogtile-byline\"><a class=\"author-name\" href=\"/authors/srivathsa-dara\">Srivathsa Dara</a><div></div></span></div>                    \n                        \n                        <div class=\"post-content\"><h2 id=\"overview\">Overview</h2> \n<p>This blog is the first in a series of blogs in which we are going to look at the disk layout of the ext4 filesystem. We will be looking at different types of on-disk structures in newly created ext4 filesystems and understand their importantance.</p> \n<p>To create an ext4 filesystem on a device, let’s say the device be sdb1, run the following command:</p> \n<div class=\"ocode ocode-initialized\"><div class=\"ocode-bttn\" data-success=\"Copied to Clipboard\" data-error=\"Error: Could not Copy\"><div><button type=\"button\">Copy code snippet</button></div><div class=\"ocode-success\">Copied to Clipboard</div><div class=\"ocode-error\">Error: Could not Copy</div></div><pre class=\"brush: bash;\" style=\"background:#eeeeee;border:1px solid #cccccc;padding:5px 10px\"><code>mkfs.ext4 /dev/sdb1</code></pre><textarea readonly=\"readonly\" tabindex=\"-1\"></textarea></div> \n<p>The <code style=\"background:#eeeeee;border:1px solic #cccccc\">mkfs.ext4</code> creates an ext4 filesystem on device <code style=\"background:#eeeeee;border:1px solic #cccccc\">sdb1</code>. <code style=\"background:#eeeeee;border:1px solic #cccccc\">mkfs.ext4</code> can take many arguments which facilitate the specification and customizaton of ext4 features. We can either enable or disable a feature depending upon our specific requirements. The default values for ext4 features for newly created ext4 filesystems is contained in the configuration file <code style=\"background:#eeeeee;border:1px solic #cccccc\">/etc/mke2fs.conf</code>. These default feature values can be overridden by specifying command line arguments to <code style=\"background:#eeeeee;border:1px solic #cccccc\">mkfs.ext4</code>.</p> \n<p>Lets take a look at the contents of <code style=\"background:#eeeeee;border:1px solic #cccccc\">/etc/mke2fs.conf</code>:</p> \n<div class=\"ocode ocode-initialized\"><div class=\"ocode-bttn\" data-success=\"Copied to Clipboard\" data-error=\"Error: Could not Copy\"><div><button type=\"button\">Copy code snippet</button></div><div class=\"ocode-success\">Copied to Clipboard</div><div class=\"ocode-error\">Error: Could not Copy</div></div><pre class=\"brush: bash;\" style=\"background:#eeeeee;border:1px solid #cccccc;padding:5px 10px\"><code>[defaults]\n        base_features = sparse_super,large_file,filetype,resize_inode,dir_index,ext_attr\n        default_mntopts = acl,user_xattr\n        enable_periodic_fsck = 0\n        blocksize = 4096\n        inode_size = 256\n        inode_ratio = 16384\n\n[fs_types]\n        ...\n        ext4 = {\n                features = has_journal,extent,huge_file,flex_bg,metadata_csum,64bit,dir_nlink,extra_isize\n                inode_size = 256\n        }\n        ...</code></pre><textarea readonly=\"readonly\" tabindex=\"-1\"></textarea></div> \n<p><strong>Note</strong>: <em>Only contents related to ext4 filesystem are displayed.</em></p> \n<p>The configuration settings for <code style=\"background:#eeeeee;border:1px solic #cccccc\">base_features</code> and <code style=\"background:#eeeeee;border:1px solic #cccccc\">features</code> are enabled by default. If we want to disable any of these or enable any other feature, we can do so using <code style=\"background:#eeeeee;border:1px solic #cccccc\">mkfs.ext4</code>. Some other default settings of interest might be that periodic fsck is disabled, the default blocksize being set to 4096 bytes, the inode size is 256 bytes and the inode_ratio is 16384.</p> \n<p>Knowing the default values of <code style=\"background:#eeeeee;border:1px solic #cccccc\">blocksize</code>, <code style=\"background:#eeeeee;border:1px solic #cccccc\">inode_size</code> and <code style=\"background:#eeeeee;border:1px solic #cccccc\">inode_ratio</code> is important because these parameters decide the number of blocks, the number of block groups and the number of inodes in a filesystem. As already mentioned, these values can be changed with <code style=\"background:#eeeeee;border:1px solic #cccccc\">mkfs.ext4</code>. Among these, <code style=\"background:#eeeeee;border:1px solic #cccccc\">blocksize</code> and <code style=\"background:#eeeeee;border:1px solic #cccccc\">inode_size</code> are self explanatory, however <code style=\"background:#eeeeee;border:1px solic #cccccc\">inode_ratio</code> needs some explanation.</p> \n<p><strong>inode_ratio</strong>: This gives the number of bytes for which, an inode is created. That means an inode is created for every <code style=\"background:#eeeeee;border:1px solic #cccccc\">inode_ratio</code> bytes.</p> \n<p>In our case, we have <code style=\"background:#eeeeee;border:1px solic #cccccc\">inode_ratio = 16384</code>, so <code style=\"background:#eeeeee;border:1px solic #cccccc\">mkfs.ext4</code> creates a inode for every 16384 bytes. If we run <code style=\"background:#eeeeee;border:1px solic #cccccc\">mkfs.ext4</code> on a 1GiB device, it creates 65536 inodes in the filesystem – as 1Gib/16364bytes = 65536. Therefore, the number of inodes in a filesystem is given by (filesystem size)/(inode_ratio).</p> \n<h2 id=\"layout\">Layout</h2> \n<p>The following are important on-disk structures of an ext4 filesystem: – Superblock – Block Group Descriptor, Group Descriptor Table – Inode Bitmap – Block Bitmap – Inode Table – Extent Tree – Hash Tree – Journal</p> \n<p>In this blog, we will cover up to the Inode Table, the rest will be covered in subsequent blogs.</p> \n<p>An ext4 filesystem is divided into block groups. Each block group has 8*blocksize (in bytes) number of blocks in it. If we consider the default blocksize, which is 4096 bytes, the number of blocks in blockgroup is given by 8*4096 = 32768 blocks in each group.</p> \n<p>Size of each block group = (Number of blocks in each group) * blocksize</p> \n<p>The number of block groups can be obtained by dividing the filesystem size by the size of each block group. (filesystem size)/(size of each block group).</p> \n<p>Generally the default block size is 4KiB, using the above formulae the number of blocks in each block group will be 32768 and the block group size will be of length 128MiB. For a 1GiB filesystem we will have 8 (1 GiB/128 MiB) block groups.</p> \n<p>Each block group has its associated block group descriptor, block bitmap, inode bitmap and inode table.</p> \n<p>So, a filesystem with 8 block groups has 8 block group descriptors, 8 block bitmaps, 8 inode bitmaps and 8 inode tables.</p> \n<p>Block group descriptors for all groups together is called the Group Descriptor Table (GDT).</p> \n<p>No.&nbsp;of inodes in each group = (Total Number of Inodes) / (No.&nbsp;block groups)</p> \n<p>Inode Table Size = No.&nbsp;of Inodes in each Group * inode_size</p> \n<p><strong>Note:</strong> <em>For simplicity, we have used 1 GiB filesystem with blocksize = 4096, inode_size = 256, inode_ratio = 16384 as an example through out the document.</em></p> \n<h2 id=\"graphical-view-of-disk-layout\">Graphical view of Disk Layout</h2> \n<p style=\"text-align:center\"><img fetchpriority=\"high\" decoding=\"async\" alt=\"Layout\" height=\"2200\" src=\"/wp-content/uploads/sites/49/2025/10/DiskLayout.jpg\" width=\"1700\"></p> \n<p><strong>Note:</strong> When flex groups are used (see below for more info), the metadata of the entire flex group is contained in the first block group of the flex group. In the above example the filesystem has only 1 flex group. So, the metadata of all block groups are contained in only the first block group.</p> \n<h2 id=\"superblock\">Superblock</h2> \n<p>On an ext4 filesystem, the first block contains the Superblock. <code style=\"background:#eeeeee;border:1px solic #cccccc\">struct ext4_super_block</code> is the on-disk structure of the Superblock. The size of <code style=\"background:#eeeeee;border:1px solic #cccccc\">struct ext4_super_block</code> is 1024 Bytes.             /* crc32c(Superblock) */\n};</code></pre><textarea readonly=\"readonly\" tabindex=\"-1\"></textarea></div> \n<h3 id=\"byte-level-view-of-an-ext4-superblock\">Byte level view of an Ext4 Superblock</h3> \n<p style=\"text-align:center\"><img decoding=\"async\" alt=\"sb1\" height=\"534\" src=\"/wp-content/uploads/sites/49/2025/10/sb_struct_1.png\" width=\"1579\"></p> \n<p style=\"text-align:center\"><img decoding=\"async\" alt=\"sb2\" height=\"534\" src=\"/wp-content/uploads/sites/49/2025/10/sb_struct_2.png\" width=\"1585\"></p> \n<p>Superblock state (0x03A to 0x03B): * 0001 – Cleanly umounted (This is the case in above hexdump) * 0002 – Errors detected * 0004 – Orphans being recovered</p> \n<p>Filesystem creator OS (0x048 to 0x049) * 0 – Linux (Linux the creator OS in the above hexdump) * 1 – Hurd * 2 – Masix * 3 – FreeBSD * 4 – Lites</p> \n<p>Superblock encrypt algorithms (0x254 to 0x257) * 0 – Invalid Algorithm (ENCRYPTION_MODE_INVALID) * 1 – 256-bit in XTS mode (ENCRYPTION_MODE_AES_256_XTS) * 2 – 256-bit AES in GCM mode (ENCRYPTION_MODE_AES_256_GCM) * 3 – 256-bit AES in CBC mode (ENCRYPTION_MODE_AES_256_CBC)</p> \n<h3 id=\"superblock-hexdump\">Superblock Hexdump</h3> \n<p><strong>Note:</strong> <em>Ext4 uses little endian notation.</em></p> \n<p style=\"text-align:center\"><img loading=\"lazy\" decoding=\"async\" alt=\"Hexdump\" height=\"556\" src=\"/wp-content/uploads/sites/49/2025/10/ext4_sb_hex.png\" width=\"850\"></p> \n<p style=\"text-align:center\"><img loading=\"lazy\" decoding=\"async\" alt=\"Description\" height=\"301\" src=\"/wp-content/uploads/sites/49/2025/10/sb-labels.png\" width=\"651\"></p> \n<p>A few important fields of the Superblock are highlighted in the hexdump. The total size of the Superblock is 1024 bytes, which spans from 0000400 to 00007ff.</p> \n<p><strong>Endianness:</strong> Ext4 uses little endian notation. In little endian notation the rightmost byte will be the most significant byte.</p> \n<p>For Example, from the above hexdump image, if we observe the magic number in the hexdump is <code style=\"background:#eeeeee;border:1px solic #cccccc\">53 ef</code>, but the actual magic number of an ext4 filesystem is <code style=\"background:#eeeeee;border:1px solic #cccccc\">0xef53</code>. As ext4 uses little endian, the most significant byte will be the right most byte. So, <code style=\"background:#eeeeee;border:1px solic #cccccc\">ef</code> is most significant byte and <code style=\"background:#eeeeee;border:1px solic #cccccc\">53</code> is least significant byte.</p> \n<p><strong>Primary and Backup Superblocks</strong> Backup copies of the Superblock are written to some of the block groups across the disk – in case the beginning of the disk gets trashed, backup Superblocks can be used for recovery. Not all blocks groups will have a Superblock copy. In our case (1GiB ext4 filesystem) apart from the primary Superblock, other copies are present in the first, third, fifth and seventh block groups. The 0th block group will host the primary Superblock.</p> \n<p>The Superblock contains a lot of information regarding the filesystem, so if the primary Superblock gets corrupted then vital information pertaining to the filesystem is compromised. To overcome such situations, backup Superblocks are stored at different places in the filesystem.</p> \n<p>In earlier versions such as ext2, backup Superblocks were created in every block group. But the ext4 filesystem has a <code style=\"background:#eeeeee;border:1px solic #cccccc\">sparse_super</code> feature, which when enabled results in backup Superblocks only being created in blockgroups 0, 1 and powers of 3, 5 and 7 (e.g.&nbsp;powers of 3 = 9, 27, 81 …..; powers of 5 = 25, 125, 625 ….; powers of 7 = 49, 343, 2401 …).</p> \n<p>Backup Superblocks and backup GDTs are never updated by the kernel. They will get updated only if any fundamental parameter of the filesystem is amended, for example, resizing the filesystem. Programs like <code style=\"background:#eeeeee;border:1px solic #cccccc\">resize2fs</code> and <code style=\"background:#eeeeee;border:1px solic #cccccc\">tune2fs</code> will change structural parameters and cause updates to the backup Superblocks and GDTs.</p> \n<h2 id=\"block-group-descriptors\">Block Group Descriptors</h2> \n<p>A block group is a logical grouping of contigous blocks, whose size is equal to the number of bits in one block. For example, in a filesystem with a blocksize of 4096 bytes, a block group will have 4096*8 = 32768 blocks. Each block group is represented by its block group descriptor, which stores information such as free inodes, free blocks and the location of the block bitmap, inode bitmap and the inode table of that particular block group.</p> \n<p>The Group Descriptor Table (GDT) contains all block group descriptors, we can call the GDT a table of block group descriptors of all block groups of the filesystem.</p> \n<p>The GDT will be present immediately after the Superblock block, and backup copies of the GDT are stored similarly to the backup copies of the Superblock. If <code style=\"background:#eeeeee;border:1px solic #cccccc\">sparse_super</code> is set then just like Superblock backups, GDT backups will be in block groups 0, 1 and powers of 3, 5, 7 (e.g.&nbsp;27, 125, 343 etc), if <code style=\"background:#eeeeee;border:1px solic #cccccc\">sparse_super</code> is not set, then these backup copies will be present in all block groups.</p> \n<p>GDTs will follow Superblocks, the primary GDT will be present in second block. Each block group descriptor is of 64 Bytes, so for a filesystem with 8 block groups there will be a group decriptor table occupying 512 Bytes (8*64) in the second block, and the remaining block will be unused.</p> \n<p>On disk block group descriptor is represented by <strong>struct ext4_group_desc</strong></p> \n<div class=\"ocode ocode-initialized\"><div class=\"ocode-bttn\" data-success=\"Copied to Clipboard\" data-error=\"Error: Could not Copy\"><div><button type=\"button\">Copy code snippet</button></div><div class=\"ocode-success\">Copied to Clipboard</div><div class=\"ocode-error\">Error: Could not Copy</div></div><pre class=\"brush: bash;\" style=\"background:#eeeeee;border:1px solid #cccccc;padding:5px 10px\"><code>/*\n * Structure of a blocks group descriptor\n */\nstruct ext4_group_desc\n{\n        __le32  bg_block_bitmap_lo; If this feature is enabled, then the number of block groups given by&nbsp;<code style=\"background:#eeeeee;border:1px solic #cccccc\">2^s_log_groups_per_flex</code>&nbsp;(<code style=\"background:#eeeeee;border:1px solic #cccccc\">s_log_groups_per_flex</code>&nbsp;is a Superblock field) are grouped as a single flex group and the inode bitmaps, block bitmaps, and inode tables of all the groups in flex group are stored in the first block group of the flex group.</p> \n<p>For example, if <code style=\"background:#eeeeee;border:1px solic #cccccc\">s_log_groups_per_flex</code> is 4 then the size of flex group is 16 (2^4) and assume that the filesystem has 48 block groups in toteal. In this case, the filesystem will have 3 flex groups, each containing 16 block groups. All the inode bitmaps, block bitmaps and inode tables of all the groups of the first flext group (0-15 block groups), second flex group (16-31 block groups), and the last flext group (32-47 block groups) will be stored in 0th, 16th, and 32nd blockgroups respectively.<br> <br> <strong>Note:</strong> This feature does not change the location of the backup Superblocks and backup GDTs.</p> \n<h2 id=\"conclusion\">Conclusion</h2> \n<p>On an ext4 filesystem, the on-disk data structures are present in the same order as discussed above. The Superblock, followed by the GDT, with the GDT pointing to the locations of corresponding block bitmaps, inode bitmaps and inode tables. When creating a filesystem, <code style=\"background:#eeeeee;border:1px solic #cccccc\">mkfs.ext4</code> creates some important structures, we have only covered up to inode tables in this blog, and future blogs will cover the rest of the data structures.</p> \n<h2 id=\"references\">References</h2> \n<ul class=\"wp-block-list\"> \n <li>e2fsprogs code – 1.46.6-rc1</li> \n <li>Kernel code-
